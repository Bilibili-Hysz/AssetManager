# 05 · 可扩展性与演进方向

## 总评

从架构形态看，这个项目已经在**为"平台化"铺路**——共享应用层、插件系统、契约测试、会话作用域，这些不是"个人工具"的必要条件，而是"多端产品"的骨架。问题是：**骨架有了，血肉（端点、UI、运维）还停留在单机工具阶段**。本节给出演进路线与方向性判断。

## 一、现有扩展点盘点

| 扩展点 | 现状 | 成熟度 |
|---|---|---|
| 插件系统 | discover/enable/load/unload + 8 种贡献 + plugin_metadata 持久化 | ★★★★☆ 能力强，但无市场/安装/更新（G2-10） |
| 应用服务层 | 15 个服务，双端共享 | ★★★★★ 最佳资产 |
| 契约层 | dto.py + contracts 测试 | ★★★★☆ 已锁定，未全面覆盖 |
| 投影失效体系 | 事件 → 失效 → 广播 | ★★★★☆ 桌面端投影尚未消费（只有 LAN 消费） |
| 权限模型 | principal + capabilities | ★★★☆☆ 有结构无上传端点（G4-1） |
| 遥测 | PerformanceRecorder | ★★★☆☆ 埋点全、查看/导出缺 |

## 二、演进方向判断

### 方向 1：深化"桌面优先 + Web 渐进"（推荐，投入产出比最高）
桌面保持完整编辑力；Web 按"浏览 → 轻编辑（备注/标签）→ 文件管理 → 上传"四步渐进（对应缺口文档 G5-1 → G4-2 → G4-1）。每一步都是纯增量：端点已可复用 FileOperationService，前端模式已成熟。

### 方向 2：真正的"多端架构"（中期）
如果未来要做移动 App / 桌面 2.0：
1. **把 LanScopedServices 提升为正式组合器**（现在靠构造函数组装），支持"任意传输层绑定任意服务集"
2. **投影失效下沉到桌面**：桌面面板也消费 InvalidationEvent（现在桌面靠信号总线直连，两套刷新机制并存）——统一后"任何端修改 → 所有端一致刷新"
3. **事件流序列化**：把领域事件序列化为持久化事件日志（event sourcing 雏形）——为"操作历史/审计/同步"铺路

### 方向 3：数据开放（最被低估的方向）
G6-1 的导出只是第一步。真正的价值在**开放数据格式**：
- 标签/备注/URL 以 JSON 导出 → 可被任何脚本/工具消费
- 定义 `.assetlibrary` 库格式（目录约定 + schema 版本）→ 库可移植
- CLI（G2-12）让高级用户脚本化整理
**数据开放 = 用户信任 = 工具长期生命力的唯一保证**。

### 方向 4：不建议的方向（我的明确否定）
- ❌ **实时协作/多人同时编辑**：当前锁模型与单库会话设计是为单写者设计的，硬改成本极高且个人场景价值低
- ❌ **微服务化/进程拆分**：LAN 服务器已独立线程运行，功能上已解耦；拆进程只会引入 IPC 复杂度
- ❌ **换 Web 前端框架**（Next.js/Remix）：静态 SPA + 后端渲染的现状正确，服务端渲染在此场景无收益
- ❌ **数据库换 Postgres**：单机 SQLite + WAL 完全够用，迁移成本巨大

关键里程碑：
1. **M1（1-2 月）**：数据安全基线 + Web 渐进编辑闭环（对应缺口路线图迭代 1-2）
2. **M2（3-6 月）**：桌面投影统一（InvalidationEvent 消费）、CLI v1、数据格式开放（导出/导入）
3. **M3（6-12 月）**：移动 Web 只读 + 插件市场雏形 + 事件日志

## 四、风险预警（演进中的"红灯"）

1. **复杂度红线**：若新增功能仍需在 runtime.py/server.py 加状态机分支 → 先做减法（02 文档建议 1-2）
2. **单点维护者风险**：整套并发协议的认知只在一人脑中——**文档化状态图**（四个协议的迁移图）应作为 M1 交付物
3. **契约漂移**：每次新增端点必须同步更新 contracts 测试 + WebUI api 客户端——否则 3 年后两端无法对齐
4. **架构迁移未闭合**（主审计 A2）：遗留 API（open_library/current/TagStore）不清理，新端（CLI/移动）会被"哪个 API 是对的"问题绊倒——M1 必须包含清理

## 五、结语

这个项目的天花板不是技术，而是**决定做什么不做什么**。它的架构已经给出了正确答案的 80%——共享服务、事件驱动、契约锁定。剩下的 20% 是：把 Web 从"浏览终端"变成"协作终端"、把数据从"私有格式"变成"开放格式"、把复杂度从"防御式"变成"必要式"。做到了，它就是一款值得被称为"产品"的工具；做不到，它仍然是这个生态里最好的个人资产管理器之一。
