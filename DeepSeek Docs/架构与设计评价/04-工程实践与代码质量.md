# 04 · 工程实践与代码质量评价

## 总评

工程实践是这套代码**最值得学习的部分**：性能工程方法论、测试纪律、迁移管理都接近商业团队水准。短板集中在：文档漂移、CI 缺口、错误处理哲学。整体 8.5/10。

## 一、测试工程（9/10）

### 亮点

1. **分层测试与架构分层对齐**：core/unit/integration/desktop/lan/panels/performance 七层，每层对应架构层——测试即文档
2. **1590 项测试的质量信号**：
   - `_cleanup_stores` autouse fixture 每测试后关连接+清事件总线（conftest）——**防测试间污染是多数项目忽略的关键纪律**
   - LAN 测试用 aiohttp test_client + 轻量线程适配器（test_server_lifecycle.py +249 行）——不依赖真实端口
   - 性能测试有基准断言（tests/performance/test_baselines.py：1K/10K 目录列表、搜索延迟）
3. **契约测试**（contracts/）：LAN 公开契约 JSON + 前端 public-contracts 测试——双端同步的守护
4. **遥测可测试性**：PerformanceRecorder 注入 + `_record_*` 全 try/except——观测不改变行为的原则写进了代码注释（如 search_service.py:187）

### 问题

1. **CI 缺口**：`.github/workflows/ci.yml` 跑 lint/typecheck/test，但：① 无性能回归门（nightly-perf.yml 存在但基准断言不阻止合并）② 无 WebUI 构建 + 前端测试步骤 ③ 无 Windows 真实环境矩阵（PySide6 只在 Linux/offscreen 验证过）
2. **测试分布偏科**：LAN 安全测试很厚，但**关闭编排/并发路径**测试虽新增 529 行仍集中在 happy path；无 fuzz、无随机化顺序运行（`pytest-randomly` 未配置）
3. **e2e 近乎缺席**：tests/e2e/ 只有零星用例；桌面 UI 全部 offscreen 验证，真实交互（拖放、托盘、多显示器）未覆盖——**可理解（个人项目），但作为"发布前冒烟"应补脚本化冒烟**

### 建议

- CI 增加：`npm ci && npm run build && vitest run`（WebUI 门禁）+ `pytest --randomly` 每周跑
- 为并发关闭区域补**压力脚本**（非断言型，跑 200 轮开/关/操作循环看崩溃率）
- 发布流程加"手动冒烟清单"文档（Windows 真实环境：启动→开库→分享→隧道→双开拒绝）

## 二、性能工程（9/10）

### 亮点（值得写进简历的方法论）

1. **先测量后优化**：PerformanceRecorder 全链路埋点（directory.list/summary、file.command、db.write_lock.wait/hold、lan.files/search/download）——**性能数据先于猜测**
2. **热点编译**：Cython 只编译 4 个纯函数热点（format_size 2.3x、is_hidden 1.5x）——**小而准**，不盲目全编译
3. **缓存分层克制**：目录摘要（SQLite）、大小/计数（file_meta 列）、缩略图（磁盘 webp + LRU）、搜索（内存索引→assets 表）——每层都有失效条件（mtime），没有玄学缓存
4. **批量意识**：`_batch_warm_file_counts` 消灭 N+1（project_service.py:130-159）、`get_tags_for_files` 900/块、缩略图批量投递
5. **打包优化有记录**：262MB → 127MB 的每一项都有文档（README：延迟 cloudflared -51.6MB、排除 Qt/PIL 模块 -31.6MB）

### 问题

1. **内存索引无上限**：`DirectoryScanner._scan_all`（scanner.py:45-68）把全库文件名+stat 载入内存——50 万文件 ≈ 100MB+ 且搜索是 O(n) 线性过滤；assets 表索引（G3-1）本可替代它
2. **`_estimate_download_size` 同步 os.walk**：目录下载前全量统计（downloads.py:51-76），大目录会卡住请求（已放 to_thread，但 500MB 检查本身耗时）
3. **home 聚合无缓存**：`get_home`（project_service.py:223）每次全库递归收集项目 + 缩略图匹配——大库首页可能秒级；应缓存 + 增量失效（投影事件已具备条件！）
4. **Cython 编译物未进版本控制**：.pyx 产物在 .Cython&Noikta/，构建链依赖本机 VS Build Tools——CI 未验证 Cython 构建可复现

### 建议

- 迭代 2 后：home 接口用 RuntimeEventRouter 失效驱动缓存（架构已铺好路，只差实现）
- 搜索主路径切换为 assets 表（G3-1），内存索引降级为"可选加速"
- 性能测试加"大库合成数据集"（5 万文件）进 nightly

## 三、代码质量（7.5/10）

### 亮点

- ruff + pyright 全量启用（pyrightconfig 覆盖整个 AssetsManager）；`from __future__ import annotations` 统一
- DeprecationWarning 迁移管理——旧 API 有明确的"废弃→替换"指引
- 注释质量高：关键算法的攻击面/竞态/为什么这么写都有说明（is_path_allowed 的 normpath 注释、unique_destination 的 TOCTOU 注释）

### 问题

1. **文件规模失控**（见 01 文档）：3 个文件超千行，9 个超 500 行——分区注释（── Section ──）缓解但未根治
2. **错误处理哲学分裂**：服务层"静默降级"（浏览路径）vs 文件操作"抛错列表"（FileOperationResult.errors）vs LAN"HTTPException"——三种模式并存，调用方要记三套
3. **魔法数字/常量漂移**：`max_depth=2`（sidebar 预加载）、`900/500` 分块、`200` 搜索上限散落各文件——应有 constants.py（目前只有 IMAGE_EXTS）
4. **类型标注不完整**：LAN 路由层大量 `Any`（LanScopedServices 字段），pyright 实际覆盖有限

## 五、总结性评价

这套代码**强在"方法论"而非"炫技"**：性能先测量、迁移有章法、测试分层、契约锁定——每一项都是可以迁移到任何项目的工程习惯。最该警惕的是**复杂度惯性**：每解决一个问题就加一层状态/锁/协议，长期会自我吞噬。建议每季度做一次"复杂度审计"（找新增的状态机、锁、兼容层），与功能开发同等重要。
