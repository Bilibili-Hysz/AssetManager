# 02 · 后端架构评价

## 总评

后端是本项目**最精彩也最危险**的部分：分层、DI、领域事件、会话作用域的设计是教科书级别的；但并发控制与关闭编排的复杂度已经逼近"一个人维护的上限"。整体评分 8/10——**方向全对，局部过重**。

## 一、架构决策逐项点评

### ✅ 1. 分层 + 依赖方向（application/domain/infrastructure）
- **判断正确**：`domain/` 零依赖（纯 dataclass + 密码学函数）、`repositories/` 只有 SQL、`application/` 不碰 Qt。这使 1590 项测试中大半能在无 GUI 环境跑
- **亮点细节**：`session_operation` 装饰器（context.py:24-38）把"会话租约"做进方法级——比在 UI 层 try/finally 关闭可靠得多
- **我的看法**：`core/` 与 `repositories/` 的边界略模糊（database.py 里既有连接池又写迁移 SQL），但功能上无碍

### ✅ 2. DI 容器（di/ + bootstrap.py）
- **判断正确**：按类注册 + 自动单例 + `LibraryScopedServices` 冻结包，是"够用即止"的好设计——没有引入 pinject/injector 这类重量框架
- **亮点**：`runtime_for()` 的**创建期并发门闩**（bootstrap.py:135-163，per-key threading.Event）——处理"两个线程同时要同一库的 runtime"的竞态，细节到位
- **我的看法**：AuthService/ShareService 故意不进容器（需 db_conn + token_secret 运行时才有）是正确的务实妥协，但应在容器里留**注册点**（现在靠 LAN 服务器硬编码创建，未来 Web 端要复用时会重复造）

### ✅ 3. 领域事件 + 投影失效（event_bus + runtime_events）
- **这是全项目最优雅的设计**：
  ```
  服务变更 → 事件(带 session_token) → RuntimeEventRouter
    → InvalidationEvent(epoch, revision, domains, paths) → WebSocket 广播
  ```
- **高明之处**：① 事件**只携带路径**而非数据（带宽/耦合双赢）② `epoch+revision` 游标让客户端能检测丢失更新并补偿（websocket.py admission barrier）③ 投影域（files/tree/home/…）把"哪些界面要刷新"声明式化
- **我的看法**：这是个人项目中罕见的"发布-订阅 + 版本游标"组合，已经接近正式实时框架（如 Hasura/PostgREST 的订阅模型）的雏形

### ✅ 4. LibrarySession 作为唯一边界
- `db_conn` 故意不属于 session 生命周期（由 DatabaseManager 管理）→ 避免连接被多 session 共享时提前关闭；`DeprecationWarning` 持续驱赶旧 API 使用者——**迁移管理有章法**

### ⚠️ 5. 并发控制：三层锁（WriteGate / 连接写锁 / owner 跟踪）
- **问题**：`_WriteGate`（读写门闩）+ 每连接 `RLock` + owner_thread/depth 重入跟踪 + 模块级 registry（database.py:39-178）——**四套语义叠加**，且 `db_write_lock()` 无参形式与有参形式行为不同
- **风险**：任何维护者改动都可能破坏"关库期间无新写者"的承诺；已用 500+ 行测试覆盖，但这是"测试驱动的复杂度"，不是"设计消除的复杂度"
- **我的判断**：功能正确（WAL 下读并发 + 写串行），但**复杂度与收益不成比例**。个人单机应用其实只需要：每连接一把 RLock + 关库前等待活跃写者（owner 跟踪可以保留，WriteGate 可以简化）

### ⚠️ 6. 四套生命周期协议交织
LibraryRuntime 状态机（open/closing/closed）+ RuntimeEventRouter（accepting/closing/drained）+ WebSocketManager（authority lease/transition）+ LibraryService（closing_roots）——每套单独看都合理，**组合后是维护者的地狱**。这不是"写错"，而是"过度防御"：每个状态转移都假设最坏并发。

### ⚠️ 7. 错误静默策略
- ProjectService/SearchService/ThumbnailService 所有 DB 异常 → `_log.debug` + 返回空（project_service.py:283-290 等十余处）
- **两面性**：浏览永不中断（用户价值）vs 用户看到"空标签/空统计"无法区分"真没有"与"坏了"（信任侵蚀）
- **我的建议**：保留静默降级，但**在返回结构里加 `warnings: [...]` 字段**，Web 端在 admin 视角显示；桌面端记入状态栏

## 二、LAN 服务器架构

### 亮点
1. **单线程事件循环 + 独立后台线程**（server.py:658-735）与 Qt 主线程完全解耦——比"在同一循环里跑 aiohttp"（很多 Qt 项目的错误做法）稳健得多
2. **中间件链职责纯净**：安全（限流/黑名单）→ 指标 → 认证，三层互不耦合；公开路径表 + 分享端点特判清晰
3. **Principal 能力模型**（principal.py）：把"你是谁"（kind）与"你能做什么"（capabilities）分离，认证与授权解耦——`/api/info` 公开但带凭据可提升身份的设计很巧妙
4. **热重载**（reload_settings :606-639）：分享名/模糊标签/深度配置免重启生效
5. **失败可诊断**：每次 start 有 8s 启动超时 + 分代清理（`_lifecycle_generation`），端口占用/启动失败有明确 OSError 而非静默

### 问题
1. **生命周期代码占 server.py 近半**（start/stop/_run/_shutdown 约 400 行）——同样是过度防御（stop 的重试/超时/竞态处理有 6 条路径）
2. **LanScopedServices 与 LibraryScopedServices 并存**：LAN 服务器在 runtime services 之上又包了一层（auth/share/activity_log/online_users）——本质是"runtime 服务 + LAN 专属状态"的组合，但没有形式化的"组合器"，全凭构造函数参数
3. **上传/文件管理端点缺失**（G4-1/G4-2）：权限模型与端点集合不匹配，是架构"半完成"的显眼证据

## 三、数据层

### 亮点
1. **Repository 批处理纪律**：900/500 分块规避 SQLite 变量上限（tag_repository.py:74-88 等）——细节专业
2. **路径迁移事务化**：move 后 tags/meta/thumbnails 三表重映射 + 物理缩略图改名（database.py:400-482）——元数据随文件移动是多数同类工具不做的事
3. **mtime 缓存失效**：目录摘要/大小缓存全部带 mtime 校验——正确、简单、够用
4. **SQL 注入防护**：LIKE 全量 `ESCAPE '\\'` 转义（防 %_ 通配）——见过太多 LIKE 注入，这里做得对

### 问题
1. **file_meta 一张表四职责**（notes/urls/大小缓存/文件数缓存）——缓存与业务数据混存，VACUUM/迁移都要牵动它；理想是拆分 `asset_meta`（业务）与 `dir_stats`（缓存）
2. **双套迁移实现**：`migrate_path_metadata`（database.py）与 Repository 的 `migrate_path` 并存——行为必须永远一致，否则文件移动后数据错乱（有测试但增加维护面）
3. **无维护工具**（G3-9）：无 VACUUM/quick_check/prune_missing 调用——数据层"能写能读"但"不体检"

## 四、我的核心建议（后端）

1. **冻结并发区域**（与主审计 D1 一致）：停止往 database.py/runtime.py 加状态，改为**压力测试**（并发开库×LAN 请求×WS 连接×文件操作）
2. **下一轮重构优先做减法**：① `db_write_lock()` 无参形式移除 ② WriteGate 简化为"关闭栅栏" ③ 合并两套 migrate_path 为一个（Repository 版为权威，database.py 版删）
3. **给容器补运行时注册点**：`container.register_runtime(AuthService)` 让 LAN 与未来 Web 编辑端点共享创建逻辑
4. **错误可见性**：降级路径加 `warnings` 输出（见 ⚠️7）
5. **保持事件架构不动**：事件 + 投影 + 游标是全项目最高价值资产，任何改动都要先写契约测试
