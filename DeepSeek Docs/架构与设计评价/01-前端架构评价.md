# 01 · 前端架构评价

## 总评

项目同时存在两套前端：**PySide6/Qt 桌面端**（成熟、功能完整）与 **React 18 + Vite WebUI**（新、功能只读）。两者共享同一套后端应用服务（经 `LibraryScopedServices` / LAN 路由），这是本架构最核心的决策——**一次实现，两端可用**。整体评分：桌面端 8/10，WebUI 7/10，双端协同 8.5/10。

## 一、桌面端（Qt）

### 亮点

1. **自绘网格（FileListGridWidget）是正确的大决策**（_grid_widget.py:44）
   - 放弃 QListView 改用 QPainter 全自绘：字体分级（9pt 粗体名 + 8pt 子行 + 6pt 徽章，:103-113）、悬停淡入淡出（`_hover_progress` :128）、选中遮罩渐变、入场错峰动画（:685-714）、`_reduce_motion` 支持（:693）
   - 这是"万级目录流畅"的根基——QListView + QIcon 在 5 万文件时会死，自绘 + 纹理缓存不会。**判断正确，执行到位**
2. **缩略图管线分层清晰**（_loader.py）：内存 LRU → 磁盘 webp → Pillow 生成，QThreadPool 异步 + 批量投递（`ThumbnailDeliveryCoordinator`）防闪烁
3. **UI 与业务彻底分离**：面板是纯渲染器（`panels/`），逻辑在 `controllers/`（无 Qt 依赖，纯 Python 可测）——这是多数个人项目做不到的纪律
4. **信号纪律明确**：`signal_bus`（低频协调）与领域事件（业务变更）分工有文档化约定（signal_bus.py docstring）

### 争议与问题

1. **大文件怪物**：info.py 1465 行、sidebar.py 996 行、sharing_settings_dialog.py 2161 行。虽然按方法分区，但单文件上千行意味着**局部状态难以推理**。个人项目可接受，继续长大会痛
2. **两代 UI 架构并存**：`_ListShim`/`_SelShim`（__init__.py:36-137）把网格伪装成 QListView 供旧代码使用——聪明的兼容但增加认知负担
3. **面板间耦合靠"爬属性"**：`window._workspace`、`panel._current`、`getattr(self, 'file_list', None)` 模式（window.py:81-92）——没有明确的接口契约，重命名一个属性可能无声断掉
4. **QSS 全量重建**：任何主题/缩放/语言变化 → `app.setStyleSheet(themes.stylesheet())` 重建全部样式（window.py:179-181）——大界面可能有可见闪烁；未用 dynamic property 细分重绘
5. **自定义窗口部件多**（title_bar/tray/workspace_bar）导致原生行为（拖动/贴边/高 DPI）需逐个手工验证

### 建议

- 为面板间通信引入**轻量接口协议**（Protocol 类），替代 getattr 探测
- 用 `themes.prop()` 把 QSS 中重复的尺寸/圆角抽成常量，减少魔法数字
- 大文件按功能拆包（info 的字段渲染 / 编辑 / 异步加载可拆三个子模块），不动逻辑只动组织

## 二、WebUI（React）

### 亮点

1. **分层简洁**：`api/`（客户端）→ `components/`（按域：layout/files/admin/shares/viewer/ui）→ 路由 5 页。每层职责单一，无状态管理库（zustand/redux 缺席但**当前规模不需要**——判断正确）
2. **契约测试是双端协作的亮点**：`public-contracts.test.ts` + `tests/contracts/lan_public_contracts.json` 锁定前后端 DTO——防止"后端改了字段前端爆炸"的经典问题
3. **实时失效设计正确**：WebSocket 只推 `projection_invalidated{epoch,revision,domains,paths}`（**事件驱动拉取**而非推送数据本身）——带宽小、语义清晰、与桌面端事件同源
4. **视觉系统统一**：CSS 变量 + Tailwind slate 系（index.css `--color-*`，暗色 #020617 底色 + indigo brand），`.light` 类已预留亮色模式
5. **Gate 首页克制**（DESIGN.md 反模式清单）——知道"哪里不做"比知道"哪里做"更难

### 争议与问题

1. **无状态管理库是正确但有时限的决定**：当前组件通过 prop 层层传递 + 各自 fetch，一旦加入"多选批量操作 + 全局搜索历史 + 实时更新合并"，prop-drilling 会失控。**建议在实现 G5-3（批量选择）前引入最小方案**（组件级 reducer 或 TanStack Query）
2. **实时合并策略缺失**：收到 `projection_invalidated` 后各组件各自重取（失效缓存），但**没有"乐观更新 + 服务端确认"机制**——编辑场景（G5-1）需要它
3. **无错误边界/骨架状态不统一**：Skeleton 组件存在但部分页面无 loading/error 三态（G5-7）
4. **路由与后端页面职责重叠**：`/browse`、`/detail` 同时被 SPA 路由（App.tsx:22-23）和后端 pages.py 定义——后端已退化为"统一返回 index.html"，应明确"后端只服务静态文件 + API"的边界（当前实现已如此，只需文档化）
5. **无障碍基线薄弱**：44px 触达目标只在 Gate 页有约束；主浏览页无 aria/键盘导航测试

### 建议

- 立即：client.ts 统一错误处理（401 跳转/503 提示/网络错误 Toast）；补路由级 ErrorBoundary
- 迭代 2（配合 G5-3）：引入 TanStack Query（缓存失效、重取、乐观更新一次解决）
- 明确双端职责分工文档：桌面=完整编辑、Web=浏览+轻编辑（或未来全编辑），避免功能竞赛

## 三、双端协同评价

| 维度 | 评价 |
|---|---|
| 代码复用 | 应用层 100% 共享（LanScopedServices 注入），这是最值钱的设计 |
| 契约一致性 | 双端各自测试锁定（1590 后端 + ~60 前端测试） |
| 实时一致性 | 同源事件 → 广播，桌面与浏览器看到的失效语义一致 |
| 功能对等 | **不对称**（Web 只读），当前是缺口（G5-1/G4-2），但**也是战略选择**——建议保持"桌面优先、Web 渐进" |
| 视觉统一 | 两套主题系统（QSS 主题 vs CSS 变量）**无共享源**——若未来要品牌统一，可考虑从主题 JSON 生成两端 token（单一来源） |

### 核心观点

双前端架构的价值排序：**共享应用层（10 分）> 契约测试（8 分）> 视觉统一（3 分）**。不要在视觉上花太多精力对齐，把精力留给功能对等与服务复用。
