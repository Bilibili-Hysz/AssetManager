# 插件 API 设计规划 · 决策文档

> **本文件夹只做检查与规划，不包含代码改动。** 目标是回答："当前插件系统为什么'定义模糊'？Blender 插件 API 到底好在哪？AssetManager 该怎样设计真正完善的插件 API？"

## 一、一句话结论

当前插件系统不是"半成品"，而是**三个半成品叠在一起**：① 文件解析器特化协议（match/parse）② 通用贡献注册（dict/位置参数混用）③ 从未生效的权限系统（死代码）。缺的不是"更多扩展点"，而是**一个统一的注册模型 + 一个运行时上下文对象 + 一套真正执行的权限门禁**——这三样恰好是 Blender 插件 API 的骨架。

## 二、方案定位（对比 Blender）

| 维度 | 当前系统 | Blender | 目标设计 |
|---|---|---|---|
| 注册模型 | 命令式回调，5 种入口协议并存 | `register_class()` 类声明式 + 注册表 | **注册表 + 类声明式**（Blender 风格） |
| 上下文 | 注册时快照（`get_selected_paths()` 构造时定格） | `bpy.context` 运行时查询 | **`PluginContext` 运行时查询** |
| 操作抽象 | 无参回调（`handler()`） | Operator：参数/撤销/poll | **Operator：参数/撤销/poll** |
| 权限 | 声明了但从未授予、只警告不阻止 | 无（Blender 信任插件） | **声明 → 授予 → 强制门禁** |
| 插件设置 | 无 | AddonPreferences | **Preferences 贡献类型** |
| 元数据 | 字段悬空（provides/config_schema 未解析） | bl_info 规范化 | **manifest v2 全字段解析** |
