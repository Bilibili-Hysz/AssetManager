# 04 · 兼容与迁移方案

> 目标：旧插件（match/parse 函数式、dict 风格注册）**零修改可运行**，新插件用 v2 API；两代共存期由兼容层桥接，最终 API.md 重写为新规范。

## 一、兼容层设计（迁移期双轨）

### 1. 旧入口协议 → 新注册表的自动适配（PluginLoader 层）

```
旧插件加载（manifest 无 api_version 或 api_version=1）
  └→ 检测入口对象形态，自动包装为 v2 类：
       模块级 match/parse  → FileParserAdapter（包装成 FileParser 类，注册到解析器表）
       模块级 register(host)  → 原样调用，但 host 换成兼容 host（见下）
       入口类/可调用对象     → CommandOperatorAdapter（注册为命令）
  └→ 诊断记录：plugin_api = "1 (legacy)"，管理器 UI 显示"旧版 API，建议升级"
```

**适配要点**：
- `match/parse` 函数签名不变（`(file_path: str)`），适配器补传构造的 `PluginContext` 占位（旧函数忽略即可）
- 旧 `register(host)` 收到的 host 是**兼容宿主**：dict 风格方法（`register_command(dict, handler)` 等）内部转换为新注册表调用——**旧插件代码无需改动**
- 兼容宿主对 10 个旧注册方法逐一映射：
  | 旧方法 | 新落点 |
  |---|---|
  | `register_command(dict, handler)` | 包装成 `CommandOperator`（无参数/无 poll，handler 收 0 参） |
  | `register_menu_contribution(dict)` | `MenuContributor` 静态项 |
  | `register_tool_window(dict, factory)` | `PanelContributor`（area 默认 right） |
  | `register_file_handler(id, match, parse)` | `FileParser` 注册表（**与旧 match/parse 实例路径合并去重**——修复 P2 双路径） |
  | `register_context_menu_item(...)` | `ContextMenuItem` |
  | `register_category(...)` | `CategoryContributor`（注册即 apply） |
  | `register_column(...)` | `ColumnContributor`（value 返回空） |
  | `register_search_provider(...)` | `SearchProvider` |
  | `register_theme_token(...)` | `ThemeTokenContributor`（注册即 apply） |
  | `hook(event_type, handler)` | `EventHook` |
  | `show_notification` | 保留（兼容 host 直通） |

### 2. 卸载对称性

旧插件 unregister：兼容宿主 `unregister_plugin(plugin_id)` 自动回收（现 host_context 已有此逻辑，迁移到注册表实现）；`unload_plugin` 的 sys.modules 清理改为命名空间包装后只删插件自己的命名空间（修复 P12）。

### 3. manifest 迁移

| 旧字段 | 新字段 | 处理 |
|---|---|---|
| `enabled` | `enabled_by_default` | 读取时两者兼容；写回只写新字段 |
| `entry`（无 :object） | `entry: "parser.py:register"` 默认 | 无变化（默认值解析） |
| `display_fields` | FileParser.output_fields / MetadataProvider.fields | 兼容层：manifest 有 display_fields 且入口是 match/parse → 自动注入 FileParserAdapter.output_fields |
| `provides` / `config_schema` / `kind` | 删除 | 不再解析（文档同步删除） |

## 二、分阶段实施计划

### 阶段 1：API 骨架（2 周）——新注册表 + 上下文 + 兼容层

| 任务 | 内容 | 验收 |
|---|---|---|
| 1.1 `plugin_api/` 包创建 | types.py（PluginContext/PluginHost/OperatorParams/12 基类声明）+ `__init__.py`（sanctioned 导出） | 空实现可 import |
| 1.2 `PluginRegistry` 实现 | register_class 类型分派到 12 张注册表；贡献回收（unregister_plugin 逻辑迁入） | 单测覆盖 12 种类型注册/回收 |
| 1.3 `PluginContext` 实现 | 从 MainWindow/文件列表/侧边栏/信息面板获取动态状态（选中/目录/焦点） | 桌面集成测试：选中文件后 ctx.selected_paths 反映 |
| 1.4 兼容宿主 | 旧 10 方法映射到新注册表；match/parse 实例路径合并去重 | **booth_link/download_tracker 不改一行代码，行为与现状一致**（关键验收） |
| 1.5 命令消费点统一 | window.py `_run_plugin_command` 与 _actions.py 路径合并为"查命令表 → poll → execute(ctx, params)" | 两处行为一致（右键与菜单执行同参数） |

### 阶段 2：能力补齐（2 周）——Operator/Panel/Preferences/Keymap

| 任务 | 内容 | 验收 |
|---|---|---|
| 2.1 CommandOperator 完整 | params 声明 → 自动参数对话框；poll 置灰；undoable → UndoService 接入 | 单测 + 手动：命令带参执行、撤销 |
| 2.2 PanelContributor 消费点 | DockFactory 注册时挂载；WindowCoordinator 打开面板 | 示例插件注册面板 → 出现在右侧 dock |
| 2.3 Preferences | plugin_prefs JSON 持久化 + 设置对话框"插件"Tab 自动表单 | 设置修改 → 重启保留 |
| 2.4 KeymapContributor | 快捷键表 + 冲突检测 | 冲突时诊断警告且不覆盖 |
| 2.5 Category/ThemeToken 生效 | register_class 时自动 apply；卸载自动回收 | 插件注册分类 → 过滤下拉可见 |

### 阶段 3：权限与生态（1-2 周）

| 任务 | 内容 | 验收 |
|---|---|---|
| 3.1 权限代理 | ServiceBundle 按授予集包装代理；advisory 记录/enforced 抛 PermissionError | 未授权写入被拒（enforced） |
| 3.2 生命周期闭环 | UI 启用即 load；重载按钮；依赖/api_version 校验；错误详情可查 | 启停/重载/缺依赖三场景 UI 正确 |
| 3.3 命名空间隔离 | 插件模块前缀 `_plugins.{id}` 包装；卸载只清自己 | 两个插件 import 同名公共模块不互相破坏 |
| 3.4 插件管理器增强 | 显示 api_version/权限/诊断/日志/贡献清单；旧版 API 徽标 | 截图级验收 |
| 3.5 文档重写 | Plugins/Docs/* 以本规范为准重写；示例插件同步新 API | API.md 与实现逐条一致 |

## 三、风险与对策

| 风险 | 对策 |
|---|---|
| 兼容层 bug 导致旧插件行为变化 | 阶段 1 验收明确"booth_link 行为与现状一致"；为旧协议补回归测试（解析结果逐字段相等） |
| PluginContext 动态查询性能 | 属性访问走 Qt 信号/属性读取（O(1)），禁止扫描；selected_paths 缓存 + 失效信号 |
| 权限代理误伤正常调用 | 代理只包"服务获取"不包"数据对象"；白名单以现有 services 方法签名为准 |
| 双轨期文档混乱 | API.md 顶部标注"v2 规范（本文件）；旧接口仅兼容"；管理器显示 api_version |
| 注册表回收遗漏 | register_class 时记录 (class, type) 对；unregister_plugin 按插件全表回收 + 单测断言"回收后贡献表为空" |

## 四、工作量与优先级

| 阶段 | 内容 | 工作量 | 前置 |
|---|---|---|---|
| 1 | API 骨架 + 兼容层 | 2 周 | 前后端分离改造的阶段 A（服务层稳定） |
| 2 | 能力补齐 | 2 周 | 阶段 1 |
| 3 | 权限与生态 | 1-2 周 | 阶段 2 |

**总计 5-6 周**。阶段 1 完成后旧插件不受影响（兼容层双轨），阶段 2 结束即可发布 v2 API 首个版本，阶段 3 完成权限闭环。
