# 施行路线图（总规划）

> 汇总全部计划（前后端分离 / 插件 API / 功能缺口 / 性能 / 视觉）的**统一施行顺序**。
> 原则：① 先基线后动工 ② 先数据安全后功能 ③ 先稳定后美化 ④ 服务层是一切地基 ⑤ 每阶段可独立中止，停止时产品都比之前好。
> 时间按个人开发（半全职）估算。

## 依赖关系图

```
阶段0 基线提交（一切前提）
  ├──▶ 阶段1 数据安全（独立）
  ├──▶ 阶段2 性能优化（独立，桌面核心）
  ├──▶ 阶段3 前后端分离 A+B（服务层稳定）
  │        ├──▶ 阶段4 视觉改进（可与3并行，表现层）
  │        └──▶ 阶段5 插件API v2（ctx.services 依赖服务层）
  │                 └──▶ 阶段7 契约化+权限（收尾）
  └──▶ 阶段6 P1功能精选（穿插空档，无硬依赖）
```

### 阶段 2：性能优化（2-3 周）【🟡 部分完成】
第 0 步测量、第 1 步 watcher 防抖与第 2 步纹理路径复用已实现；第 3 步目录大小治理已完成“单并发 + 有界队列 + 可见目录优先”子项，第 4 步已补充无变化 refresh 的 reset 复用行为证据，但未改变首次 loading reset。50,000 synthetic/offscreen 结果：cold grid.frame P50 `6.436ms`，scroll/zoom P50 `3.713ms`、P95 `10.853ms`，warm `texture_build_count=0`。
**验收未闭合**：真实图片 IO/目录协议入口已提供，但仍需要发布机执行；目录大小首屏耗时、reset/刷新语义和完整性能门禁仍待验收。

### 阶段 3：前后端分离 A+B（2-3 周）【服务层地基】
按 [前后端分离改造计划/02](前后端分离改造计划/02-推荐实施计划.md)：A1 URL 剥离（✅）→ A2 校验下沉（标签、分享、目录摘要✅）→ A3 按端装配（✅）→ B1 Runtime-owned Auth/Share（✅）→ B2 缩略图走服务（✅ 服务边界已提交，性能/全量验收待闭合）→ B3 投影统一（Desktop TagTree + Web 活动标签重拉已形成最小闭环，最终跨端状态验收待办）。
**验收边界**：`rg "/api/" AssetsManager/application` 为空；TagService、ShareService 与 AssetService 已拥有 A2 业务校验，LAN 仅保留 transport/PathGuard 边界并翻译 `ValidationError`；A3 保持单一 Runtime/snapshot，Desktop/shared 服务 eager，Asset/Project/Search 仅在 LAN 组合时 single-flight materialize；B1 由 `RuntimeSharingServices` 持有 `AuthService`/`ShareService`/Runtime 级 `token_secret`，Desktop 用 `ShareCreationTask` 直调，LAN 复用同一服务，HTTP `/api/shares` 管理链路保留；ThumbnailLoader 只持有 ThumbnailService 与 immutable Runtime snapshot。已有报告中的 Python `1695 passed, 1 skipped`、Task D `431 passed`、跨端矩阵 `190 passed` 是历史证据快照，不代表本轮 B1 后最终计数；B2 真实图片 IO/性能、全量回归与 B3 最终跨端状态仍待验证。
**门禁**：阶段 C（契约化）可推迟，本阶段完成即达"边界规则落位"核心目标。

## 里程碑定义

| 里程碑 | 时间点 | 产品状态 |
|---|---|---|
| **M1 可用性基线** | ~3 周 | 数据安全闭环 + 掉帧缓解——可放心日常使用 |
| **M2 边界立起** | ~6 周 | 服务层稳定 + 视觉 V1——架构可演进 + 观感提升 |
| **M3 生态起步** | ~10 周 | 插件 v2 骨架 + P1 精选——第三方可接入 |
| **M4 平台收尾** | ~14 周 | 契约化 + 权限门禁——可被任何人接手 |

**任何里程碑后都可暂停**：M1 后是"安全的工具"，M2 后是"结构清晰的产品"，M3 后是"有生态的平台"。

## 并行与风险

| 并行组合 | 说明 |
|---|---|
| 阶段 1 ∥ 阶段 2 | 文件域不重叠（core/application vs panels/file_list） |
| 阶段 3 ∥ 阶段 4 | A3 前置已满足；后续按 B1（bootstrap/dialogs）与视觉 panels 文件分区 |
| 阶段 6 穿插任意阶段 | 单任务独立提交 |

| 风险 | 对策 |
|---|---|
| 阶段 3 中途停止 | A1-A3 与 B1 已形成独立交付检查点；可在 B2/B3 最终验收前暂停而不回退现有边界 |
| 阶段 5 兼容层 bug | booth_link 回归快照测试与兼容层同日落地 |
| 并行时文件冲突 | A3/B1 的 bootstrap、dialogs、LAN 与 panels 注入点已存在交叉依赖；后续视觉任务仍需按文件域分区认领 |
| 时间不足 | 砍单顺序：阶段 7 C3 → 阶段 5 阶段2 → 阶段 4 V2/V3 → 阶段 6 尾部 |

## 执行约定（沿用各计划文档）

1. 每个任务独立 commit（`feat:/fix:/refactor:`），消息风格沿用仓库
2. 先加测试后改代码；行为等价任务以测试锁 JSON/行为
3. 每阶段结束跑全量门禁：`pytest -q` + `tests/performance` + 契约测试
4. 静态验收项（边界规则 5 条）写入 `docs/architecture.md`
5. 店铺方向（[未来方向/01-04](未来方向/README.md)）触发条件未满足前不进入任何排期
