# 03 · 应用服务层

应用层共 14 个服务，按职责分四组。**桌面端与 LAN 端共享同一套服务实例**（经由 `LibraryScopedServices`），这是本项目架构的核心价值点。

## A. 库与文件操作组

### 1. `LibraryService`（library_service.py）
见 [02-入口与启动链路.md §5](02-入口与启动链路.md)。开库/关库/会话生命周期唯一入口。

### 2. `FileOperationService`（file_operation_service.py）—— 文件操作总闸

**数据流特征**：所有操作 = 文件系统变更 + 索引刷新 + 元数据迁移 + 领域事件发布。

| 方法 | 功能 | 事件 |
|---|---|---|
| `create_folder` (:82) | 新建目录（自动去重 "New Folder_1"…） | FileCreated, FileSystemChanged |
| `rename` (:102) | 目录内改名（委托 move） | — |
| `move` (:112) | 移动/改名；`_migrate_metadata` 迁移标签/元数据/缩略图；刷新索引 | FileRenamed, FileSystemChanged |
| `copy_to_directory` (:139) | 批量复制（文件/目录树） | FileCopied, FileSystemChanged |
| `move_to_directory` (:176) | 批量移动 | FileRenamed, FileSystemChanged |
| `duplicate` (:208) | 复制重命名 `name_copy.ext` | FileCreated, FileSystemChanged |
| `delete_permanent` (:228) | 永久删除；`_clear_deleted_projection` 清理标签/元数据/缩略图文件/索引 | FileDeleted, FileSystemChanged |
| `delete_to_trash` (:280) | send2trash 回收站 | 同上 |
| `restore_backup` (:255) | 撤销恢复备份 | FileCreated, FileSystemChanged |

安全机制：
- `_assert_under_root`（:22-24）：所有路径必须 resolve 后位于库根内
- `unique_destination`（:360-386）：`os.open(O_CREAT|O_EXCL)` 原子保留名字，防 TOCTOU 竞态
- `session_operation` 保证操作期间 session 存活

索引一致性：移动/删除后调用 `_refresh_parents` / `_refresh_after_move` / `_refresh_directory_tree` 同步 `assets` 索引表；删除时 `_clear_deleted_projection`（:299-323）在 `db_write_lock` 内级联删除 tag/meta，并物理删除对应 `.webp` 缩略图。

遥测：`_measure_command` 装饰器（:26-59）记录 `file.command` 性能事件；`suppress_command_telemetry` 用于撤销/重做场景防止重复计数。

### 3. `UndoService`（undo_service.py）—— 按库隔离的撤销/重做

- 栈按 `library_root` 隔离（:37-45）；深度默认 20
- **删除可撤销靠备份**：`prepare_delete` 把文件/目录复制到临时目录（`AssetsManager_undo_*`）→ 删除成功后 `commit_delete` 入栈；失败则 `discard_delete` 清理备份
- `perform_undo`（:208-235）：先在栈顶执行反向操作（rename→move 回来；delete→`restore_backup`），**成功后才出栈**（乐观锁校验栈顶未变）
- `cleanup()`（:323）：关库时删除整个备份目录

## B. 浏览/检索组

### 4. `AssetService`（asset_service.py）—— 纯文件系统浏览

- `list_directory(root, target, options)`（:70-131）：
  `os.scandir` → 过滤（隐藏文件/排除模式/分类/搜索/深度）→ 目录摘要（`_scan_dir_summary` 一次扫描同时取首图+文件数，走 DirectoryCache）→ 排序（`sort_key_for_entry`：目录永远在前）→ 汇总（总数/总大小/格式化）
- `summarize_directories`（:133-148）：批量摘要（LAN `/api/files/summaries` 用）
- `_entry_to_item`（:153-217）：目录带 `is_project` 标记（按 project_depth 判定）
- 目录摘要缓存语义（`_scan_dir_summary` :232-283）：mtime 不一致即失效重扫；批量写入缓存

### 5. `SearchService`（search_service.py）—— 三种检索路径

| 方法 | 数据源 | 用途 |
|---|---|---|
| `search_by_tags` (:40) | `file_tags` 表（LOWER 大小写不敏感） | 标签检索 |
| `search_by_name` (:74) | 内存索引 `DirectoryScanner`（LAN 服务器后台全库扫描） | 快速文件名搜索 |
| `search_by_name_indexed` (:118) | `assets` 索引表（SQL LIKE/子串） | 索引兜底 |

LAN 搜索策略（metadata.py handle_search）：标签优先 → 内存索引 → 索引表兜底。所有路径带性能遥测与失败降级（返回空列表而非 500）。

### 6. `ProjectService`（project_service.py）—— 项目视图

"项目"= 目录树中达到深度阈值的目录（默认 `ProjectDepthConfig.global_depth=2`，可按一级分支覆盖，来自设置 `sidebar_depth_cfg`）。

- `list_projects` (:84)：候选目录 → 批量预热 file_count 缓存（`_batch_warm_file_counts` 避免 N+1）→ 组装条目（首图缩略图 URL / 标签 / 目录大小 / 文件数 / 备注）→ 排序（项目排前）→ 分页
- `get_home` (:223)：递归收集项目 → 附加缓存缩略图（DirectoryCache 命中 → `_attach_baked_thumbnails` 用 thumbnail_cache 表做二级匹配）→ 最近 20 个 / 预览墙 / 热门标签(前20) / 统计
- `build_tree` (:356)：目录树（按深度配置裁剪为叶子）
- `get_project_detail` (:301)：文件清单+图片清单+标签+备注+URL+下载 URL
- 所有 DB 查询带 try/except 降级（日志 debug），**不因缓存失败而中断浏览**——健壮性设计

### 7. `AssetIndexService`（asset_index_service.py）—— assets 表维护

- `index_directory` (:15)：单目录扫描 upsert；非 force 且有存量则跳过
- `index_directory_tree` (:58)：`os.walk` 强制全树索引
- 查询：`query_by_parent` / `query_by_extension` / `search_by_name`
- 删除：`remove_entry` / `remove_directory`（文件操作后一致性维护）
- 注意：索引是**懒填充**的——只有经过 FileOperationService 的目录或显式调用才会写入

## C. 元数据/标签组

### 8. `TagService`（tag_service.py）

- 全部经 `TagRepository` 访问 `file_tags`/`tag_metadata`
- **规范名解析**：`get_library().canonical(tag)`（tag_library.py 多语言同义词表）→ 用户输入"贴图"自动落库为 "Texture"（:99）
- 变更事件（:54-71）：`TagsChanged`（无会话）+ `AssetTagsChanged`（带 session_token，供 Runtime 投影）+ `TagCatalogChanged`（标签目录变化）
- 批量：`get_tags_for_files` 分块 IN 查询（900/块）
- `TagServiceAdapter`（:231-257）：把 TagService 包装成 TagStore 协议，供 TagEditorDialog 使用——**兼容层**的典型例子

### 9. `MetadataService`（metadata_service.py）

- `get_metadata`（:75）：一次性取 tags+notes+urls（两个 Repository）
- 备注/URL CRUD，变更发布 `AssetNotesChanged` / `AssetUrlsChanged`
- **目录大小缓存**（`get_dir_size` :129）：三层策略：库根总大小（library_stats）→ 缓存（cached_mtime ≥ 目录 mtime 即命中）→ `ProjectData.compute_dir_size` 全量递归扫描后写缓存
- 文件数缓存：`batch_get_cached_file_counts` / `batch_set_cached_file_counts`（批量预热用）

### 10. `ThumbnailService`（thumbnail_service.py）

- `thumbnail_cache_key`（:28-50）：`sha256(解析路径|mtime)[:16]`，内存缓存 8192 条避免重复 syscall
- `resolve`（:84-105）：磁盘缓存命中（`.webp`）→ 原图（仅图片扩展名）；`max_size>=1024` 视为原图请求跳过缓存
- `process_image`（:107-132）：Pillow 打开 → 高斯模糊（敏感标签，radius=15）→ 等比缩放（LANCZOS）→ WEBP 质量 80
- `_check_blur`（:143-163）：blur_tags 与文件标签交集判定（敏感内容打码）

## D. 分享/认证组（LAN 专用）

### 11. `ShareService`（share_service.py）

- `create_share`（:33-67）：随机 10 位 id（碰撞重试 5 次）→ 密码 PBKDF2 哈希 → 到期时间戳 → 落库 → 返回 `ShareLink` 值对象
- `validate_access`（:139-155）：分享存在性 → 密码 token 校验 → 到期/限次 → 路径范围校验（`is_path_allowed`）
- token：`generate_share_token`（1 小时有效，HMAC 签名）

### 12. `AuthService`（auth_service.py）

- 用户认证：`authenticate_user` → `generate_user_token`（24h）
- 注册：用户名规则（2+ 字符、字母数字_−）、密码强度校验（8+/大小写/数字/特殊字符/弱密码黑名单）、邀请码逻辑（**存在活跃邀请码时强制要求**）
- 用户管理：activate/deactivate、邀请码生成/吊销
- 令牌校验走 `domain/auth.py` 纯函数 + `AuthRepository` 取用户

### 13. `PluginService`（plugin_service.py）

薄门面：包装 `PluginManagerService`，提供 discover/list/enable/disable/load/unload/load_all_enabled/get_commands/get_menu_contributions。无状态，跨库共享。

## 数据流要点

1. **写路径统一**：任何标签/元数据/文件变更 → 领域事件（带 session_token）→ RuntimeEventRouter → 投影失效 → LAN WebSocket 广播。桌面端则由面板直连 service + Qt 信号刷新。
2. **读路径分层缓存**：目录摘要（SQLite directory_cache）→ 文件数/大小（file_meta 缓存列）→ 实时扫描；搜索走内存索引 → assets 表 → 实时。
3. **降级优先**：ProjectService/SearchService/ThumbnailService 的 DB 异常几乎都吞掉降级，保证浏览不中断（代价是错误静默，见风险文档）。
