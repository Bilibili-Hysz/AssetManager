# 01 · 方案利弊分析

> 针对"前后端分离不明确"问题，给出四个候选方案并逐一评估。每个方案包含：定义、利、弊、风险、适用边界、结论。

---

## 方案 A：最小修补（打补丁）

**定义**：只修最痛的两处——① 分享创建改进程内调用 ② 服务层 URL 泄漏暂不改（或只改不动响应）。其他保持现状。

| 利 | 弊 |
|---|---|
| 成本最低（3-5 天） | 边界规则依然无成文，下次新功能继续绕路 |
| 风险几乎为零 | 桌面缩略图仍绕过服务，双端语义漂移隐患仍在 |
| 分享功能不再依赖服务器运行 | DTO 三份手抄继续漂移，契约维护成本持续 |
| | 新服务默认全捆绑的耦合从创建处继续扩散 |

**风险**：低。但这是"止痛药"，不是"治疗"——六个月后问题清单原样回来。

**适用边界**：只适合"一周内必须发布且无后续开发"的冻结期。当前项目处于活跃演进期，不适用。

**结论：❌ 拒绝**（治标不治本，代价只是推迟）

---

## 方案 B：行为等价重构（推荐）

**定义**：以"边界规则"为目标（应用层去传输化、展示层不碰数据层、进程内不走 HTTP、校验只在服务层、按端装配），用**测试锁定行为等价**，三阶段渐进落地。每步可独立提交、可独立回滚、可中途停止。

| 利 | 弊 |
|---|---|
| 风险低：1590 项测试 + 契约测试是行为等价的安全网 | 总工期 4-6 周，中期存在"两套并存"过渡态 |
| 收益确定且立竿见影：URL 剥离、分享直调、缩略图走服务 | 阶段 C（契约化）若范围失控会拖期 |
| 渐进可停：任何阶段停止，系统都可用 | 需要维护者理解"边界规则"并持续执行 |
| 与现有架构完全兼容：不改传输方式、不换框架 | 部分重构（如桌面投影统一）牵动面板层 |
| 边界清晰度可达 85%：规则成文 + 代码落位 | — |

**风险控制**：阶段门禁（每阶段全量测试 + 冒烟）；行为等价重构全部走"先加测试→改代码→验证"顺序；URL 剥离用契约测试证明响应 JSON 不变。

**适用边界**：适用于"系统活跃演进、边界已明确要立、但不想承担破坏性风险"的绝大多数情况。

**结论：✅ 推荐**。它是唯一同时满足"风险可控 + 收益确定 + 可中途停止"的方案。

---

## 方案 C：全 HTTP 客户端化（桌面也走网络）

**定义**：OpenAPI 为唯一契约，桌面端放弃进程内调用，全部改走本地 HTTP 客户端（生成 SDK），实现"三端同构"。

| 利 | 弊 |
|---|---|
| 边界最清晰：唯一契约、唯一传输方式 | **性能灾难**：文件列表/缩略图每次网络往返 + JSON 序列化，自绘网格的高性能优势被抵消 |
| 桌面/Web/移动三端代码模式完全一致 | **单点故障**：桌面功能依赖本地服务器进程，服务器启动失败则桌面不可用（当前分享创建已受此害，方案 C 把危害扩大 10 倍） |
| 契约自动生成，杜绝手抄漂移 | **复杂度爆炸**：本地也要做 token、超时、重试、版本兼容——分布式系统的全部问题 |
| | 现有 1590 项测试大部分要重写为 HTTP 集成测试 |
| | 与"独立线程事件循环"的 LAN 架构冲突：桌面高频操作被自身后端限流（限流器按 IP） |

**核心论证**：**进程内调用不是"分离不彻底"，而是性能与可靠性的资产**。分离要统一的是"接口定义与边界规则"，不是"传输方式"。把桌面改造成 HTTP 客户端是"为了架构而架构"——用确定性高的新问题（性能/可用性）替换低确定性的旧问题（边界模糊）。

**结论：❌ 明确否决**。方向性错误，不因"三端统一"的诱惑而接受。

---

## 方案 D：超前重构（服务全中立 + 桌面全投影 + 事件序列化）

**定义**：在方案 B 基础上追加：① 所有服务返回值彻底传输中立 ② 桌面面板全部改为订阅 InvalidationEvent 刷新 ③ 领域事件序列化为事件日志（event sourcing 雏形）。

| 利 | 弊 |
|---|---|
| 长期架构最干净，双端刷新语义 100% 统一 | 周期 10+ 周，个人项目难以持续投入 |
| 事件日志为审计/同步/多端铺路 | 收益集中在最后 15% 的边界清晰度，边际递减 |
| 未来移动端接入成本最低 | 桌面投影改造牵动全部面板，回归风险集中在后期 |
| | 事件序列化引入存储与版本管理的新复杂度 |

**适用边界**：适合"有明确多端产品规划 + 团队 ≥2 人 + 无发布期限压力"的场景。当前为个人项目，**宜将其中"桌面投影统一"降级为方案 B 阶段 C 的可选子任务**，其余留作远期。

**结论：⏸ 留作远期**，不否定价值，但不在本轮执行范围。

---

## 方案对比总表

| 维度 | A 修补 | **B 重构（推荐）** | C 全 HTTP | D 超前 |
|---|---|---|---|---|
| 成本（人周） | 0.5-1 | 4-6 | 6-10 | 10+ |
| 风险 | 低 | **低** | 高 | 高 |
| 边界清晰度提升 | +10% | **+45%** | +55%（代价错误） | +55% |
| 桌面性能影响 | 无 | 无 | **显著倒退** | 无 |
| 可中途停止 | — | **✅ 是** | 否（半途更糟） | 否 |
| 测试策略 | 现有 | **行为等价 + 契约守护** | 大量重写 | 大量新增 |
| 与我前几套文档的衔接 | 无 | 缺口的 P0/P1 部分可顺带完成 | 冲突 | 远期 |

---

## 推荐方案 B 的论证摘要（为什么不是其他）

1. **为什么不是 A**：问题已在扩张（DTO 三份手抄、服务越权每次新功能都在加码），拖延使成本单调上升
2. **为什么不是 C**：传输方式统一 ≠ 边界清晰；进程内调用是资产，方案 C 用确定的新问题换旧问题
3. **为什么不是 D**：价值集中在尾部，个人项目执行期内大概率中途流产；其唯一有价值的部分（桌面投影统一）已降级为 B 的可选阶段 C
4. **为什么是 B**：测试基础设施（1590 项）恰好是行为等价重构的完美安全网——这是本项目比其他项目更适合做这类重构的原因
