## 问题重述（一句话）

当前"分离"是**为 WebUI 可用而抽象**，不是**为边界而抽象**：共享服务层名义 14 个、实际双端只用 2 个；应用层直接产出 `/api/` URL；桌面端绕路 HTTP 调自己的后端；展示层持有裸 Connection/Repository。边界规则无成文，契约三份手抄。

## 方案矩阵（速览）

| | 方案 A 最小修补 | **方案 B 行为等价重构（推荐）** | 方案 C 全 HTTP 客户端 | 方案 D 超前重构 |
|---|---|---|---|---|
| 思路 | 只修最痛的两处 | 边界规则立起来，测试护航渐进改 | 桌面也走 HTTP，三端统一 | 服务全中立 + 桌面全投影 |
| 成本 | 3-5 天 | **4-6 周** | 6-10 周 | 10+ 周 |
| 风险 | 低（但边界仍模糊） | **低（1590 测试锁定行为）** | 高（性能/可靠性倒退） | 高（周期长收益递减） |
| 边界清晰度 | 40% | **85%** | 95%（但传输层错误统一） | 95% |
| 与现状兼容 | 好 | **好（渐进可停）** | 破坏性 | 破坏性 |
| 我的结论 | 治标不治本 | **✅ 推荐** | ❌ 方向性错误（详见 01） | 留作远期 |

## 推荐结论

**执行方案 B**，分三阶段：**止血（1 周）→ 走正门（1-2 周）→ 契约化（2-4 周，按需）**。
前置条件：先提交工作区未提交的 LibraryRuntime 迁移改动（主审计 A1），保证基线干净可回滚。
