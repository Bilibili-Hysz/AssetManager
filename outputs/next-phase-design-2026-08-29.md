## 一、产品定位重述（设计的出发点）

AssetManager 是**个人/小团队的视觉资产库**：桌面端是库所有者的"管理台"（整理、打标、维护、分享管理），Web 端是局域网/隧道访客的"消费面"（浏览、搜索、下载）+ 商城（买家/卖家）。LAN 服务按库单实例——这个架构决定了一个关键设计事实：

> **桌面端的深度 = 所有者的效率上限；Web 端的体验 = 库的"门面质量"，决定分享给别人的第一印象。**

本会话的修复已把两端的"正确性问题"（危险默认值、透明遮罩、静默失败）清掉。下一阶段的主题应该从"修错"转向"**双端各就其位**"：

- **Web 端：从"能用"到"配得上分享"**——访客的搜索、浏览、下载体验，以及门面（Gate/画廊/商城）的视觉完成度。
- **桌面端：从"操作可用"到"操作可信"**——所有者每天高频动作的反馈闭环（撤销可见、错误分级、状态行动化）。
- **系统层：双端一致性成为默认**——主题同源已打通（`gen_web_tokens.py`），把它变成产品能力而不是构建细节。

## 二、四条设计主线（含取舍）

### 主线 A：访客体验纵深（Web，建议主推）

**论点**：工具的 LAN 分享能力是差异化卖点（README 权限模型、隧道、商城都为此服务），但访客侧的检索与浏览深度明显弱于桌面。补齐它直接放大整个产品的价值。

| # | 功能 | 设计要点 | 粒度 |
|---|---|---|---|
| A1 | **Web 主题选择器** | `gen_web_tokens.py` 从 2 主题扩到 24 主题（输出 `[data-theme="xxx"]` 变量组而非只 `html.light`）；Gate/页头加主题下拉；服务端可下发"跟随库主当前主题"（`/api/info theme_color` 已有，升级为主题名）；访客选择存 localStorage，匿名身份不落库 | M |
| A2 | **搜索与发现**：历史 + 明示过滤 | 搜索历史（localStorage，最近 10 条，下拉回填，桌面 FileListController 同思路）；标签过滤当前是单值点击，补 AND/OR 切换并**明示当前逻辑**（filter bar 显示"风景 AND 人物"）；结果计数常显 | M-L |
| A3 | **快捷键速查** | Web 已有 Ctrl+K / g / s 但不可发现；加 `?` 浮层列出全部快捷键（数据结构化，桌面 F1 帮助页同模式），顺手把 g/s 的单键作用域写进文档 | S |
| A4 | **PWA**：manifest + 离线壳 | LAN 手机访问是核心场景；SW 缓存 app shell（不含 API），"添加到主屏"；安装后图标/启动屏。注意 vite 插件选型要锁版本（依赖上限策略） | M |
| A5 | **下载任务中心** | DownloadProgress 顶栏扩展为可展开队列：进行中/完成/失败（配额不足、403），失败可重试；批量 ZIP 大文件时给"完成后通知我"（Notification API，需授权流程） | M |

**顺序建议**：A1 → A2 → A3（一周内可全部落地）；A4/A5 随后。

### 主线 B：所有者操作可信（桌面，执行既有优化方案）

桌面优化方案批次 1/2（见 `desktop-uiux-optimization-plan-2026-08-29.md` 路线图）仍然全部开放，无需重新设计，直接执行：

- **批次 1 快赢**（S 级，建议立即排）：焦点样式补齐（QComboBox/:focus、checkbox 非纯色指示）、CJK 三项（字体回退链/缩放下限/全角标点）、撤销可发现（操作反馈加"· Ctrl+Z"后缀）、设置保存语义统一、错误分级决策表落地。
- **批次 2 结构**：按钮默认层级（双源：themes.py+stylekit.py 需同步改）、空态行动化、错误行内化（error_no_library 9 处弹窗清零）、列表视图、快捷键双源收敛。
- **批次 3 标签域**：TagBrowserDialog 去模态化两阶段（先非模态+导航衔接，后 `tag_filter_changed` 第 8 信号 + 多标签 AND/OR——与 A2 的 Web 侧 AND/OR 是同一个领域概念，**建议一次设计两端实现**）。

### 主线 C：双端一致性（系统层，与 A/B 并行做地基）

1. **设计令牌语义对齐**：桌面 13+25 令牌 vs Web COLOR_MAP 28 变量——间距/圆角/字号语义已有，但**动效令牌**（desktop `properties.animation.duration_ms` vs web 无）、**状态色语义**（hover/disabled/skeleton）没有跨端契约。建议在 `gen_web_tokens.py` 的映射表加注释锚定"每个 Web 变量对应桌面哪个令牌语义"，缺失的补齐。
2. **基础组件体系**：Web 抽 Button/IconButton/Input/EmptyState 四件套（评审 P1-5）；桌面 StyleKit 收敛单例（reports 遗留）。两端各自有组件规范文档（一页纸：何时用 primary/secondary/ghost/danger——桌面 set_button_variant 与 Web buttonVariant 语义表）。
3. **门禁对称**：桌面有 check_style_sources（px/hex 门禁），Web 新增了 check_web_token_usage——把"Web 禁原生色类（slate-/indigo-）"也立规（现有 184 处存量逐步清偿，新增即红）。

### 主线 D：性能与架构债（按需偿还，不阻塞主线）

已知仍开放的 P1/P2：桌面 stderr 重定向锁串行化解码、关窗/切库串行 drain、Web RealtimeContext 全树重渲染、AuthProvider 巨型 Provider、纹理缓存无字节上限。这些都有明确修复方向（见各评审报告），建议**在任何出现可感知卡顿的时机插入偿还**，而不是专项排期。

## 三、两个跨域设计（需要先想清楚再动手）

### 3.1 标签 AND/OR 检索——一次设计，两端实现

这是桌面（TagBrowserDialog 去模态化阶段 2）与 Web（A2）共享的领域概念，值得一份统一设计：

- **领域模型**：过滤态 = 标签集合 + 组合逻辑（ANY/ALL）+ 排除集（可选，二期）。这是纯后端能力扩展（search/gallery 投影加参数），桌面 TagTreePanel 与 Web filter bar 都只是它的两个视图。
- **交互规格（两端一致）**：选中 ≥2 标签时显示组合切换器（"任一匹配 / 全部匹配"），当前逻辑常显；计数实时反馈"匹配 N 项"；清空一键可达。
- **后端工作量**：`/api/search`、`/api/gallery/*` 加 `match=any|all` 参数 + 桌面 `search_service` 同步；契约 golden 更新（`lan_public_contracts.json` + `gen_ts_types --check`）。
- **建议**：作为 A2+桌面批次 3 的共同前置，先落后端与契约，两端 UI 跟进。

### 3.2 Web 端操作可信性——明确"不做完整撤销"

Web 无撤销栈、后端无 undo API。完整撤销 = 后端命令化改造（操作日志 + 逆操作），投入大且与桌面撤销体系（本地服务层）难以统一。**建议的设计立场**：

- Web 端不做撤销，改做**破坏性操作的三重防护**：确认框默认按钮安全（桌面已修，Web 侧确认弹窗统一走 Modal + 默认 Cancel）→ 高危操作（删除标签/商品下架）二次输入确认或 typed confirmation → 操作后 toast 显示受影响对象与"在桌面端可撤销"提示（跨端兜底话术，诚实且低成本）。
- 该立场写进 ADR，避免后续反复讨论。

## 五、需要你拍板的决策点

> **工作默认值（2026-08-29，用户未即时选择，按推荐项先行；任何一条可推翻）**：
> 1. 优先级总纲 = **主线 A 访客优先**（N2 起步）；
> 2. 主题选择器范围 = **跟随库主当前主题**（生成器只输出库主主题一套变量，亮暗切换保留；24 主题全量可选留作后续升级）；
> 3. 商城 = **冻结**（买家链路已完整，资源转向访客体验与双端一致性）；
> 4. Web 破坏性操作 = 采纳 3.2 折中立场，落地时补 ADR。

1. **商城的战略权重**：claim/配额/批量标签完成后，商城买家链路已完整。要不要深化卖家侧（运营分析页 `shop/analytics` Web 已有 API 消费、订单导出已有）？还是冻结商城、聚焦访客体验（主线 A）？
2. **主题选择器的范围**：24 主题全量下发 Web（访客可选任意主题）vs 只做"跟随库主当前主题"（访客无选择权，观感与桌面一致）。后者实现更小、产品语义更"库主主导"，前者更自由。**我倾向后者起步 + 亮暗切换保留**。
3. **Web 破坏性操作立场**（3.2）：接受"确认 + 提示桌面可撤销"的折中吗？接受则写 ADR。
4. **优先级总纲**：主线 A（访客）与主线 B（所有者）哪个先？我的默认建议是 **A 先**——理由：桌面刚经历过一轮大修+审计循环，边际收益递减；而 Web 访客体验是"库的门面"，且改动都在 webui 单体里，回归面小、验证快（offscreen/vitest/axe 全套门禁齐全）。
