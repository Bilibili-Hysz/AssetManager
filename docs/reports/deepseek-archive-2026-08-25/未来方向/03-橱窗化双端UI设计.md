# 03 · 橱窗化双端 UI 设计（WebUI）

> **状态：🔵 设计参考（随店铺方向同批确认，暂不开发）**
> 本文回答两个问题：① 当前 WebUI 的整体设计思路是什么 ② 橱窗化时是否需要"分享者/被分享者"双端分离 UI、如何设计。

## 一、当前 WebUI 设计思路复盘（事实基础）

### 1. 结构总览（webui/src，已核对）

```
路由（App.tsx）
├── /           LandingPage（Gate 首页：预览墙 + 身份感知）
├── /login      LoginPage
├── /browse     BrowsePage（项目网格/列表 + 侧边栏 + 信息面板）
├── /detail     DetailPage（项目详情 + 图片画廊）
└── /s/:shareId ShareReceivePage（分享接收）

分层
├── pages/      页面编排
├── layouts/    AppLayout（Header/Sidebar/StatusBar/ResizablePanel）
├── components/ 按域：files（ProjectGrid/Card/LayeredPreview/Breadcrumb/FileToolbar）
│               admin（User/Invite/Share/OnlineUsers/ActivityLog）
│               shares（ShareDialog）viewer（ImageViewer）ui（Modal/Toast/Skeleton/…）
├── hooks/      数据层：useAuth/useWebSocket/useInvalidation/useProjects/useSearch/
│               useThumbnailCache/useTheme/useMediaQuery/useI18n
├── stores/     AuthContext（登录态）RealtimeContext（投影失效）
├── api/        客户端：client.ts + auth/files/metadata/shares/system/tags/thumbnails/users
└── types/      api.ts（契约类型）
```

### 2. 三条设计主线（橱窗化要继承的原则）

1. **身份感知渲染，而非身份跳转**：LandingPage 通过 `/api/info` 的 `principal` 反射身份——guest 看到"进入库"，登录者看到"进入工作区"。**不强制登录、不重定向**，同一页面按身份变换内容（DESIGN.md 决策：Gate 是身份过渡态）
2. **实时失效管道统一**：`RealtimeContext` + `useInvalidation` 消费 WebSocket `projection_invalidated`（epoch/revision/domains）——任何端修改，所有端按域失效。**这套管道天然支持"买家看到新上架、卖家看到新订单"**——同一管道，不同投影
3. **契约锁定**：`types/api.ts` + public-contracts 测试——双端 UI 增加时，契约先行

### 3. 现状的缺口（橱窗化的起点）

| 缺口 | 说明 |
|---|---|
| 分享页是"孤岛" | `/s/:shareId` 只有单文件/单分享交付，无店面上下文（无店名/品牌/相关商品） |
| 浏览页是"内部工具"形态 | BrowsePage 的 Sidebar/InfoPanel/管理组件是卖家任务流，对买家过重 |
| 无"价格/购买"概念 | 现有模型里只有"分享"，没有"商品" |
| 无订单/交易视图 | admin 组件是用户/分享管理，无订单 |

## 二、核心决策：双端分离的"度"

### 决策 1：双端需要不同 UI——✅ 是（分离视图域与布局）

| 维度 | 买家端（Storefront） | 卖家端（Dashboard） |
|---|---|---|
| 任务流 | 逛 → 买 → 下载（3 步） | 商品 → 订单 → 店面 → 统计（管理） |
| 访问性 | 公开（无登录或轻登录） | 登录后（admin/owner） |
| 布局 | 品牌化头 + 宽栅格 + 移动优先 | 现有 AppLayout（Header/Sidebar/StatusBar） |
| 信息密度 | 低（展示导向） | 高（管理表格） |
| 实时语义 | "新上架/售罄" | "新订单/发货状态" |

### 决策 2：不拆两套应用——✅ 同一 SPA，双视图域

- **共享 60-70% 组件**：ProjectCard/ProjectGrid/LayeredPreview/ImageViewer/缩略图缓存 hooks/下载流程/TagChip/Toast/Modal
- **共享全部数据层**：api/、hooks/、stores/（AuthContext 扩展为"身份 + 域"）
- **共享实时管道**：同一 RealtimeContext，按域订阅不同投影（这呼应后端 `RuntimeEventRouter` 的 domains 设计）
- 拆两套应用的后果：双倍契约维护、双倍构建、组件漂移——**纯负收益**

### 决策 3：路由与布局域分离（代码结构）

```
/（域路由：身份感知分发）
├── /store/*          Storefront 域（买家，公开，StorefrontLayout）
├── /s/:shareId       兼容保留（旧分享链接不失效）
├── /app/*            Dashboard 域（卖家，登录守卫，AppLayout）
└── /browse /detail   现有浏览保留（卖家资产库核心）
```

**域守卫**（前端）：`AuthContext` 记录 principal → 路由级 `<RequireDomain domain="shop" />` 守卫，未授权显示"此区域需要运营者权限"（而非 403 裸页）。

## 三、买家端（Storefront 域）设计

### 页面

| 路由 | 页面 | 数据源（现有可复用） |
|---|---|---|
| `/store` | **店面首页**：店名/logo/公告 + 预览墙（现有 Gate 墙复用）+ 商品分类筛选 + 搜索 | `/api/info`（品牌字段）+ `/api/home`（preview_pool 已是"商品墙"雏形） |
| `/store/:itemPath` | **商品页**：大图预览墙 + 文件清单 + 价格 + 购买按钮 + 卖家公告 | `/api/projects/{path}`（ProjectDetail 已有文件清单/图片/备注——**就是商品详情页的数据模型**） |
| `/store/checkout` | **购买流程**：确认订单 → 支付（PaymentProvider：收款码展示/外链跳转）→ 等待确认 | 新端点 `/api/shop/order` |
| `/store/delivery/:token` | **交付页**：购买成功的限次下载（复用现有分享下载端点） | `/api/shares/{id}/download` |

### 设计原则（继承 DESIGN.md 的 Gate 哲学）

- 买家端**不出现任何管理 UI**（无侧边栏、无用户管理、无统计数字）
- 品牌化：店名/logo/主题色/公告（现有 `lan_theme_color`/`welcome_msg`/`footer_text` 设置扩展为店面配置）
- 移动优先：单列 + 大触达目标（DESIGN.md 已有 375px 约束，扩展到全部店面页）
- 状态明确：加载（Skeleton）/不可用（503 已处理）/空店（"店主尚未上架商品"）

## 四、卖家端（Dashboard 域）设计

| 路由 | 页面 | 说明 |
|---|---|---|
| `/app` | **概览**：今日订单/销售额/库存（复用 StatsResponse 思路） | 新 |
| `/app/items` | **商品管理**：库内目录 → 商品表格（价格/封面/状态），上架/下架/改价 | 新（桌面端可并行上架，双向同步） |
| `/app/orders` | **订单管理**：待确认/已发货/已撤销 + 发货操作（生成限次链接） | 新（orders 表） |
| `/app/store` | **店面配置**：店名/logo/公告/主题色/支付方式（PaymentProvider 配置） | 扩展 sharing_settings |
| `/app/assets` | **资产库**（现有 /browse + /detail 迁入此域） | 保留 |

卖家端复用现有 admin 组件模式（表格 + 操作对话框），布局沿用 AppLayout。

## 五、共享层清单（双端复用，禁止复制）

| 共享件 | 现有位置 | 双端用法 |
|---|---|---|
| 预览墙 | LandingPage 的 Gate 墙 | 买家：店面墙；卖家：商品选择器 |
| ProjectCard/Grid | components/files | 买家：商品卡片（+价格角标）；卖家：库内浏览 |
| LayeredPreview/ImageViewer | components/files, viewer | 两端预览 |
| 缩略图管线 | useThumbnailCache | 两端 |
| 下载流程 | ShareDialog/DownloadProgress | 买家：交付下载；卖家：测试下载 |
| 实时失效 | RealtimeContext/useInvalidation | 买家投影：items；卖家投影：orders/items |
| TagChip/Toast/Modal/Skeleton | components/ui | 两端 |
| i18n（en/ja/zh） | i18n/ | 两端（店面词条新增） |

**原则**：任何组件进入共享层必须两端可见用例；仅一端使用的组件留在域内（如 admin 表格、店面 hero）。

## 六、身份与权限映射（现有 principal 模型扩展）

```
现有：guest / user / admin  ← principal.py 已定义
扩展映射：
  买家   = guest（公开店面）+ user（注册买家，可查订单历史）
  卖家   = admin（工作台全权）
前端域守卫 = AuthContext.principal.capabilities：
  /store/*  → 无守卫（公开）
  /store/checkout → 轻登录（可选，MVP 可不登录直接付款码下单）
  /app/*    → capabilities.manage_links（复用现有 admin 判定）
```

**不需要新权限维度**——现有 capabilities 已能表达；新增 `shop` 能力维度留给店铺版开发时按需加。

## 七、渐进实施路线（橱窗化 = 现有代码的"域化 + 增量"，非重写）

### 阶段 S1：店面只读（1-2 周，零后端新功能）
- `/store` = LandingPage 的预览墙 + BrowsePage 的网格，换 StorefrontLayout
- 商品 = 现有项目目录（深度配置内的目录自动成为"商品候选"）
- **验证点**：买家体验链路（逛→看详情）在现有 API 下跑通——证明"橱窗 80% 已在库中"

### 阶段 S2：商品化（2-3 周）
- `shop_items` 表（目录 → 商品：价格/封面覆盖/上下架）+ 桌面"上架"入口
- 商品页加价格/购买按钮；店面首页只显示已上架商品
- 后端：`/api/shop/items`（复用 ProjectService 组装）

### 阶段 S3：交易闭环（3-4 周）
- checkout 页 + PaymentProvider（收款码模式先行）+ `orders` 表
- 交付：订单确认 → 生成限次分享链接 → 交付页（复用 `/s/` 与 share 下载端点）
- 卖家端 `/app/orders` + `/app/store` 配置

### 阶段 S4：工作台完善（2-3 周）
- `/app/items` 商品管理、概览统计、双端实时（新订单 → 卖家 WebSocket 通知）

**总工时约 8-12 周**（与 01 店铺文档的 MVP 对齐）；每阶段结束都可独立发布。

## 八、关键设计决策记录

| # | 决策 | 理由 |
|---|---|---|
| 1 | 双端不同 UI，同一 SPA 双视图域 | 任务流差异大但共享组件密度高；拆应用是纯负收益 |
| 2 | 域守卫用前端路由 + 现有 capabilities | 不引入新权限系统 |
| 3 | 店面首页继承 Gate 设计哲学 | 预览墙/品牌化/移动优先已验证（DESIGN.md） |
| 4 | 商品数据模型 = 库内目录 + 价格元数据 | 复用 ProjectService/缩略图/分享全链路 |
| 5 | 交付走现有分享链接机制 | 限次/限时/计数已实现，零新下载代码 |
| 6 | 买家端不做"注册强制" | 收款码模式无需账号即可下单（MVP），降低转化摩擦 |
