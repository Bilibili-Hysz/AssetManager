# 06 · 前后端分离深度分析

> 本文回答三个问题：**现在的前后端到底怎么分的？哪里分得不彻底？怎么分才明确？**
> 所有论断基于代码取证（见文末证据附录），不是印象式评价。

## 一、现状拓扑：理想 vs 实际

### 理想中的分层（文档宣称）

```
桌面端(Qt) ──┐                       ┌── 应用服务层（共享）──┐
             ├── 同一套服务 ────────→ │ Asset/Tag/Meta/...   │ → 数据层
WebUI(React) ─┘                       └──────────────────────┘
```

### 实际的依赖关系（代码取证）

```
┌────────────────────────── 桌面进程 ──────────────────────────┐
│ Qt 面板/对话框                                               │
│   ├─→ LibraryScopedServices（15 个服务全捆绑，实际只用 8 个）   │
│   ├─→ 直接使用 Repository：ThumbnailLoader→ThumbnailRepository│
│   │        InfoController→PluginMetadataRepository           │
│   ├─→ 直接拿 DB 连接：_base.py:250, info.py:1058             │
│   └─→ HTTP 调自身 LAN 服务器（分享创建/统计）：_share_api.py   │
└─────────────────────────────┬────────────────────────────────┘
                              │ 进程内调用           │ HTTP
                              ▼                       ▼
┌─────────────────────── 共享应用服务层 ─────────┐  ┌─── LAN 服务器（aiohttp）───┐
│ 双端共用: TagService, MetadataService          │  │ 中间件链（安全/认证）        │
│ 仅桌面: FileOperation, Undo, Plugin, AssetIndex│  │ 路由 = 控制器职责 + 业务规则 │
│ 仅LAN:  Asset, Project, Search, Thumbnail,    │  │ 服务访问器 get_*_service    │
│        Share, Auth                            │  │ 桌面端专用服务在此创建:       │
└──────────────────────────────┬────────────────┘  │ AuthService/ShareService    │
                               │ 进程内调用           └──────────┬────────────────┘
                               ▼                                 ▼
                          数据层（SQLite/文件系统）          WebUI (React)
```

**核心发现：这不是"一个后端两个前端"，而是"两个后端 + 三个前端"**：
1. **进程内后端**（应用服务）——桌面专用，无接口契约
2. **HTTP 后端**（LAN 服务器）——WebUI 专用，契约测试保护
3. 共享层只有 TagService/MetadataService 真正双端复用，其余 12 个服务各归其主

## 二、分离不彻底的十个具体问题（按严重度排序）

### 问题 1 [严重] 应用服务层泄漏 HTTP 语义
`project_service.py` 中 8 处、`search_service.py:30-32` 构造 `/api/thumbnails/...`、`/api/download/...` **URL 字符串**。

- 后果：① 应用服务"知道"传输协议——桌面端一旦消费这些服务，拿到的是指向不存在后端的 URL ② 换端点前缀（如挂到 `/api/v2`）要改服务层 ③ 测试要模拟 HTTP 语义
- 根因：ProjectService 是"为 LAN 而生"的服务（docstring 说"shared by LAN routes and future desktop views"），作者直接把响应组装做了进去
- **这违反的是分层第一原则：应用层返回值必须是领域/传输无关的**。正确做法：服务返回 `PreviewRef(path: Path)` 值对象，URL 由**传输层**（路由/前端）负责拼装

### 问题 2 [严重] 桌面端用自己的 HTTP 后端
`dialogs/_share_api.py`（QRunnable + requests 调 `http://localhost:{port}/api/shares`）、`share_link_dialog.py:159`、`sharing_settings_dialog.py:1021-1038`（/api/stats）。

- 后果：① 同一份业务（分享链接）桌面走 HTTP、Web 走 HTTP、但**逻辑实现只存在于 LAN 服务器**——服务器没启动，桌面连"创建分享链接"都用不了（即使本可直接调用服务）② 桌面端要自己拼 URL、注入 token、处理 10s 超时与网络异常——**把进程内调用硬生生改造成分布式调用** ③ 测试需要 mock HTTP
- 根因：AuthService/ShareService 因"需要 db_conn + token_secret"被排除在容器外（bootstrap.py 模块 docstring），导致桌面无进程内入口，只能走后门 HTTP
- 正确做法：把 AuthService/ShareService 注册进容器（session 打开后创建），桌面直接调用；HTTP 端点保留给 WebUI。**进程内能办的事不要走网络**

### 问题 3 [严重] 展示层直连数据层（绕过服务）
- `_loader.py:231`：`ThumbnailLoader`（Qt 组件）持有 `ThumbnailRepository` + `sqlite3.Connection`
- `info_controller.py:80`：`InfoController` 直接构造 `PluginMetadataRepository(db_conn)`
- `_base.py:250`、`info.py:1058`：面板把 `session.connection_for()` 的裸连接传给 UI 组件

- 后果：① 桌面缩略图缓存逻辑**绕过 ThumbnailService**（所以 ThumbnailService 纯 LAN 用，双端行为不一致的隐患：桌面与 Web 的缩略图缓存语义可能漂移）② 换存储（如缩略图改文件哈希目录）要改 UI 层 ③ 测试 UI 必须先造数据库
- 根因：桌面缩略图管线（_loader.py）在 WebUI 出现**之前**就存在，是"先有 UI 后有服务"的历史遗留——服务层是为 WebUI 补的，桌面没有同步迁移

> **处理状态（2026-08-15）**：`info_controller.py` / `info.py` 的裸连接已移除——`InfoController` 改由 `LibrarySession` 派生连接（`db_conn` 可选、缺省时 `session.connection_for()`），插件仓库走新增的 `PluginMetadataRepository.for_session(session)`；`info.py` 不再传 `connection_for(...)`（提交 `1a194e6`）。缩略图 `_loader.py` 的 ThumbnailService 迁移属方案 B 的"桌面缩略图改走 ThumbnailService"，另见 `02-推荐实施计划.md` 阶段 B。

### 问题 4 [严重] 路由层承载业务规则（无法复用）
- `routes/shares.py:95-113`：密码 4-128 字符、过期 1-8760 小时、限次 1-10000——**业务规则写在 HTTP handler 里**
- `routes/files.py:149-167`：summaries 的 48 条限制、唯一性、直子目录校验
- `routes/tags.py:39-65`：标签长度 200 字符限制

- 后果：① 桌面端要实现相同规则（如将来桌面也建分享）无从复用 ② 规则变更要改路由 + 重测 HTTP ③ 控制器层（桌面有、LAN 无）与路由层职责不对称
- 正确做法：校验下沉到 Service（`ShareService.create_share` 内完成，抛 `ValidationError`），路由只做参数提取与异常翻译

### 问题 5 [中等] LibraryScopedServices 是全捆绑，不是按需
`bootstrap.py:173-197` 为每个 session 创建 15 个服务，其中桌面只消费 8 个（Asset/Project/Search/Thumbnail 4 个纯 LAN 服务白创建——AssetService 附带的 `DirectoryCache` 还会开连接建缓存表；DatabaseIntegrity/LibraryExport 属于后台与后续设置/CLI 能力）。

- 后果：① 每库白建 4 个服务 + 1 个缓存实例 ② **"什么服务属于什么端"没有任何地方声明**——新服务进来默认两端捆绑，耦合从创建处开始
- 正确做法：服务声明 `endpoint`（desktop / lan / both）属性，bootstrap 按端点装配；至少把"桌面用不到的服务"从桌面装配中剔除

### 问题 6 [中等] DTO 三份同步无单一事实来源
`lan/dto.py`（Python 手写）↔ `webui/src/api/*.ts`（TS 手写）↔ `tests/contracts/lan_public_contracts.json`（快照）。同步靠契约测试强制，但**任何一端都是"手抄本"**。

- 正确做法（按成本递增）：① 最小：契约 JSON 改为**生成物**（从 dto.py 生成或 openapi 生成 TS 类型，CI 校验一致性）② 中策：引入 OpenAPI 规范作为唯一来源，路由装饰器校验请求/响应 ③ 上策（不做）：GraphQL

### 问题 7 [中等] 桌面没有接口契约，WebUI 有
WebUI 有 `api/` 客户端 + 契约测试保护；桌面面板**直接调用服务方法签名**——改 `TagService.add_tag` 的签名，桌面 6 处引用 + 测试全要跟着改，且没有任何一层"翻译"。

- 正确做法：桌面引入**薄适配层**（`application/desktop_ports/`：面板只依赖的 Protocol/接口集合），面板与实现解耦——这也是让桌面面板可独立测试的钥匙

### 问题 8 [中等] 两套通知机制，两套世界观
桌面：`signal_bus`（Qt 信号）+ `_event_bridge`（领域事件→信号）+ 面板直连服务刷新。WebUI：WebSocket `projection_invalidated`。

- 后果：同一事件在桌面走 3 条路径、在 Web 走 1 条路径——**桌面投影体系（RuntimeEventRouter）只被 LAN 消费**，桌面面板自己是另一套刷新逻辑。同一份"失效语义"两个实现
- 正确做法：桌面面板逐步改为订阅 `InvalidationEvent`（投影域 files/tags/metadata 已覆盖桌面需要），signal_bus 退化为纯展示协调（其 docstring 本来就是这么宣称的——只是没做到）

### 问题 9 [轻微] 控制器层是桌面独有
LAN 路由承担了"参数整理 → 调服务 → 组装响应"（即控制器职责）；桌面控制器（controllers/）是纯逻辑层。**同一职责两种归宿**。

- 轻微，因为两边各自自洽；但若未来桌面也要走 HTTP（如移动端管理），需要第三个"控制器"——说明职责没有稳定命名

### 问题 10 [轻微] `Any` 泛滥掩盖边界
`LanScopedServices`（_helpers.py:39-61）全部字段 `Any`——绑定检查在 `_LanServerImpl.__init__` 里手写（server.py:139-161 逐个比对 provider），**类型系统没有参与约束**。服务绑定错误要到运行时才炸。

## 三、根因分析：为什么变成这样

1. **时间序**：桌面（Qt 直连数据层）→ WebUI 出现 → 为 WebUI 抽服务层（application/）→ 服务层"名义上共享、实际为 LAN 写"→ 桌面没有回头迁移
2. **动机偏差**：抽象是为"WebUI 能用"而做，不是为"桌面/Web 分界"而做——所以 ProjectService 直接产 HTTP URL、ShareService 只活在服务器里
3. **缺边界定义**：从没回答过"应用层返回值里允不允许出现 /api/ 字符串""UI 层能不能拿裸连接""桌面要不要走 HTTP"——这些规则没有成文，靠作者手感
4. **重功能轻契约**：桌面一直能用，迁移收益看不见，就停在了"够用"——符合个人项目"没人催就不重构"的规律

## 四、目标架构：边界规则（建议成文）

```
┌─ 展示层 ────────────────────────────────────────────────────┐
│ Qt 面板/对话框          React 页面          LAN 路由(薄)      │
│   └ 只依赖: 桌面适配层     └ 只依赖: api/    └ 只依赖: 服务     │
├─ 接口契约层 ─────────────────────────────────────────────────┤
│ DesktopPorts(Protocol)          OpenAPI 规范（生成 TS/DTO）   │
├─ 应用服务层 ─────────────────────────────────────────────────┤
│ 领域值对象进出；禁止出现: /api/、HTTP、Qt、AppSettings 直读    │
├─ 领域层 ─────────────────────────────────────────────────────┤
├─ 数据层 ─────────────────────────────────────────────────────┤
```

**五条边界规则（每条对应一个现存违规）**：
1. **应用层返回值/参数不允许出现 URL、HTTP、传输语义**——缩略图返回 `Path` 引用，URL 在传输层拼（修问题 1）
2. **展示层不允许持有 Connection / Repository**——桌面缩略图/插件字段全部走服务（修问题 3）
3. **进程内能调用就不走 HTTP**——AuthService/ShareService 进容器，桌面直调（修问题 2）
4. **业务校验只存在服务层**——路由只做参数提取 + 异常 → HTTP 状态翻译（修问题 4）
5. **每端只装配自己用的服务**——服务声明端点属性（修问题 5）

## 五、分步改造方案（低风险优先，每步可独立提交）

### 阶段 A：止血（1 周，纯重构不改行为）
1. **服务层 URL 剥离**：ProjectService/SearchService 返回 `PreviewRef(Path)`；路由层 `_to_url()` 统一拼 URL。跑全量测试 + 契约测试确认响应 JSON 不变（这是**行为等价重构**，测试就是安全网）
2. **校验下沉**：ShareService.create_share 内置全部校验（抛 ValidationError）；路由 catch 后返回 400。行为等价
3. **桌面服务装配收敛**：LibraryScopedServices 拆 `desktop_bundle` / `lan_bundle`，bootstrap 分别装配（LAN 侧在 _LanServerImpl 已有 LanScopedServices，顺势统一）

### 阶段 B：桌面走正门（1-2 周）
4. **AuthService/ShareService 进容器**：`ApplicationBootstrap.create_lan_services(session, token_secret)` 注册；`share_link_dialog.py` 改调 `ShareService.create_share` 进程内（保留 HTTP 端点给 WebUI）；`_share_api.py` 中分享创建部分删除，统计部分可留（纯展示数据）
5. **桌面缩略图改走 ThumbnailService**：ThumbnailLoader 的 Repository 访问迁移到服务方法（`desktop_thumbnail_cache()` 端口），UI 层不再持有连接

### 阶段 C：契约化（2-4 周，与功能缺口迭代 2 并行）
6. **OpenAPI 最小引入**：先给 LAN 写端点自动生成 TS 类型（脚本读 dto.py 或手写 openapi.yaml 一份为源），替换 contracts 快照
7. **桌面端口层**：`application/desktop_ports/` 定义面板依赖的 Protocol（如 `TagsViewPort`），面板改造为依赖接口；逐步替换 getattr 探测
8. **桌面投影统一**：InfoPanel/TagTree/FileList 订阅 InvalidationEvent（domains 已覆盖），signal_bus 收窄为纯展示

## 六、改造收益与风险

### 收益
| 指标 | 现在 | 改造后 |
|---|---|---|
| 服务层 HTTP 泄漏 | 8+ 处 URL | 0 |
| 桌面绕过服务的数据访问 | 3 处直连 | 0 |
| 分享创建路径 | HTTP 往返（依赖服务器运行） | 进程内直调 + HTTP 双路径 |
| 双端刷新语义 | 桌面 3 套 / Web 1 套 | 统一投影 |
| 新服务接入成本 | 默认全捆绑 | 按端点声明 |
| 契约同步 | 三份手抄本 | 单一来源生成 |

### 风险与控制
1. **行为等价重构的最大风险是"改了但没保持行为"**——对策：阶段 A 每步全量跑 1590 测试 + 契约测试 + LAN 集成测试
2. **桌面投影统一（B8）牵动面最大**——放到最后，且先只迁移 InfoPanel 一个试点
3. **OpenAPI 引入若做重会卡死**——坚持"够用"：只覆盖 WebUI 用到的端点，不做全量
4. 与缺口文档的衔接：阶段 B 的 4 同时解决 G4-5 认证缺口的前置；阶段 C 的 7 配合 G1-1/G5-3 落地

## 七、一句话结论

**你现在的"分离"是"为 WebUI 而抽象"，不是"为边界而抽象"**——所以共享层是名义的、桌面是绕路的、规则是散落的。不需要推倒重来：阶段 A 三个行为等价重构（URL 剥离、校验下沉、按端装配）+ 阶段 B 两条走正门（分享进容器、缩略图走服务），就能把边界立起来；阶段 C 的契约化是让边界**可维护**的关键。全部工作约 4-6 周，每一步都有测试护航，不会伤及现有 1590 项测试覆盖的行为。
