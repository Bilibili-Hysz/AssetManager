# 07 · WebUI 前端薄弱项审计（2026-08-22）

**范围**：`webui/src/`（api/stores/hooks/pages/components/types/i18n/入口/路由）、`webui/e2e/`（6 spec）、package.json、vite/tsconfig/vitest 配置。生产源码 117 文件 15,640 行（含测试 28,774 行）。
**基线**：commit `5fbf930` 脏工作树。

## 总体评估

这是一份少见的高纪律前端代码库：类型逃逸几乎为零（生产代码仅 1 处带 eslint-disable 的 `any`，0 处 `as unknown`/`@ts-ignore`）、tsconfig 开满 strict + `noUncheckedIndexedAccess`、无任何 `dangerouslySetInnerHTML`、所有外部 URL 渲染点都做了 http/https 协议白名单过滤、外链均带 `rel="noopener noreferrer"`。S1-S5 批次的收敛是真实的：15 个 api 工厂统一走 `createApiClient` 单点错误分类（401/403/429/503 + Retry-After），GET 重试与指数退避在 `utils/backoff.ts` 单源；`useCachedQuery` 的缓存键序列化、in-flight 去重、订阅者注册表与 `clear()` 的协同、gc 计时器归属检查等竞态细节都经过深思（含测试）。认证凭据全程 HttpOnly cookie，前端不接触令牌，401 的身份重置用路径白名单避免了"输错密码被登出"。i18n 三语字典 605 键完全对齐，零缺失。

薄弱项集中在四类：**(1) 下载超时的"总预算"实现与"停滞预算"注释语义不符**，大文件/慢速链路下 5 分钟硬顶会杀掉仍在正常流动的传输；**(2) 卖家域客户端混用**——`useSellerShopApi` 专为例外场景而生，但三个卖家页面里只有 SellerSettingsPage 用了它，SellerOrdersPage/SellerProductsPage 走主会话客户端，卖家 cookie 过期时的 401 会级联成主会话整体登出；**(3) 类型双源**——`types/contracts.ts` 由脚本生成，而手写的 `types/api.ts` 重复定义了其中 5 个 DTO，后端变更时存在静默漂移面；**(4) 覆盖缺口**——S2 静态门禁只管 `pages/`，`components/layout/Sidebar.tsx` 直接 import api 工厂并手写获取逻辑；e2e 的真实后端验收默认 skip，axe 扫描未覆盖购物车/结算/交付/订单等 10+ 页面。

数据层的失效链路（WS 事件 → epoch/revision 游标去重 → gap 检测 → /revision 恢复 → 域匹配 → abort+refetch）完整且有恢复失败的可观测标志，未发现旧响应覆盖新响应的路径。整体评级：**良好，无 P0**。

## 主要发现（按严重度排序）

### [P1][正确性] 下载超时是"总时间预算"而非注释声称的"停滞预算"，大文件传输会被中途杀死 ✓已复核
- 位置：`webui/src/api/client.ts:35-36、309、367`
- 证据：`DOWNLOAD_TIMEOUT_MS = 5 * 60_000`；`requestBlobResponse` 与 `requestBlobWithProgress` 均只调用一次 `withTimeout(signal, DOWNLOAD_TIMEOUT_MS)`，内部 `setTimeout` 在流式读取循环（:392-399 `reader.read()`）中**从不续期**。注释写着 "give them a much longer stall budget"、"a stalled download cannot hang forever"，但实现是整个请求+读取的总时长上限。
- 影响：单文件下载与批量 zip 超过 5 分钟即被 abort，即使数据仍在持续到达。LAN 上 GB 级资产包在 Wi-Fi/慢盘场景下（约 <20MB/s）就会触发，表现为"下载总是在 5 分钟整失败"。
- 建议：在每次 `onProgress`/`reader.read()` 到帧时重置停滞计时器（真停滞预算），或至少将预算放大并改为按进度续期。

### [P1][认证/正确性] 卖家域三个页面有两个走主会话客户端，卖家 401 会重置主会话身份
- 位置：`webui/src/pages/SellerOrdersPage.tsx:33`、`webui/src/pages/SellerProductsPage.tsx:24`（均 `useShopApi()`）；对照 `webui/src/hooks/usePageApis.ts:63-70`（`useSellerShopApi` 的存在理由注释）与 `webui/src/pages/SellerSettingsPage.tsx:21`（唯一正确使用的页面）
- 证据：`useSellerShopApi` 注释明确写着"uses the SellerAuthContext dedicated client so a seller-session 401 is never interpreted as a main-session expiry"；但 SellerOrdersPage 的 `fulfillOrder/revokeOrder/rotateDelivery`（:44,61,78）和 SellerProductsPage 的 `shopApi.list(undefined, true)`（:63）都走 `useAuth().api`——该客户端带全局 `onUnauthorized` → `handleUnauthorized` → `clearGuest(true)`。`useCommerceCatalog(true)`（SellerProductsPage.tsx:25，useCommerce.ts:210-229）同样用主客户端。
- 影响：【确认】代码路径不一致；【疑似，取决于后端授权】当卖家 cookie 过期而主会话仍有效时（SellerAuthContext.tsx:44-47 明确说这种翻转是设计内场景），这两个页面的请求 401 会把主会话整体登出（清缓存、清缩略图、跳登录页），而 SellerSettingsPage 同场景只报错。存在探测（seller-status）与请求之间的竞态窗口。
- 建议：卖家表面统一改用 `useSellerShopApi`，或让 `useCommerceCatalog` 接受客户端参数。

### [P2][可靠性] WebSocket 无心跳/半开连接检测，睡眠唤醒后可长时间静默失效
- 位置：`webui/src/hooks/useWebSocket.ts:57-77`
- 证据：客户端只挂 `onopen/onmessage/onclose/onerror`，无 ping/keepalive，无周期性活性探测；RealtimeContext 的 gap 检测只在**收到事件**时触发（RealtimeContext.tsx:178-205）。
- 影响：笔记本休眠/网卡切换/NAT 静默丢链后，TCP 半开连接不触发 `onclose`，StatusBar（StatusBar.tsx:77）持续显示"已连接"，投影失效事件全部丢失且无恢复动作，直到 OS 层 TCP 超时（可达十几分钟）。
- 建议：加应用层心跳（周期发 ping、超时未 pong 主动 `ws.close()` 触发重连），并监听 `window online`/`visibilitychange` 强制一次 `recover()`。

### [P2][认证] 主会话登出不清理卖家会话
- 位置：`webui/src/stores/AuthContext.tsx:141-147`（logout 只调 `authApi.logout` + 清本地）与 `webui/src/stores/SellerAuthContext.tsx:97-105`（卖家登出独立）
- 证据：两个会话完全隔离清理；`logout()` 不触碰 seller cookie，也不通知 SellerAuthProvider。
- 影响：共用电脑场景下，用户 A 登出主会话离开，卖家 cookie 仍在浏览器里；用户 B 打开 `/seller` 时 SellerAccessGate 的状态探测会直接放行 A 的卖家身份。LAN 环境风险中等，但违背"登出清理完整性"预期。
- 建议：主登出时同时调用 `auth/seller-logout`（或后端在主登出时联动失效卖家 cookie）。

### [P2][类型漂移] types/api.ts 手写复制了生成契约中的 5 个 DTO，双源无同步校验
- 位置：`webui/src/types/api.ts:9-17、22-24、33-40、64-70、72-87`（Capabilities/RuntimeCursor/UserResponse/SessionPrincipal/ProjectionDomain）vs `webui/src/types/contracts.ts`（AUTO-GENERATED by scripts/gen_ts_types.py）
- 证据：两文件同名同形接口并存；RealtimeContext 从 contracts 导入 RuntimeCursor，AuthContext 从 api 导入 SessionPrincipal——结构化类型让两边暂时兼容，但后端 `lan/dto.py` 变更后只有 contracts.ts 会被重新生成。
- 影响：契约漂移不会在编译期暴露，直到某处同时消费两个版本才可能炸；也稀释了"生成是唯一事实源"的规则。13 个 `.contract.test.ts` 只覆盖响应 fixture，不覆盖类型定义本身。
- 建议：让 `types/api.ts` 从 `types/contracts.ts` re-export 这 5 个类型，或让生成脚本同时产出两文件。

### [P2][架构] S2 数据获取门禁有盲区：components/ 直接 import api 工厂 + 多处手写获取逻辑绕过 useCachedQuery
- 位置：`webui/src/components/layout/Sidebar.tsx:7-8`（`import { createMetadataApi } from '../../api/metadata'` 等）与 `:129-151`（手写 generation 守卫获取）；`webui/src/pages/DetailPage.tsx:52-100`（手写 abort+generation）；`LegacyStorefrontItemPage.tsx:36-53`；`StorefrontBuyerOrdersPage.tsx:51-92`
- 证据：`scripts/check_frontend_data_fetch.py` 的 `PAGES_DIR` 只扫 `webui/src/pages`，Sidebar 这类组件直接建工厂不会被拦。DetailPage/StorefrontBuyerOrdersPage 的手写逻辑本身有完整的 abort+generation+statusRef 三重守卫（质量不低），但缓存受益（去重、失效、retain-on-error）全部旁路。
- 影响：同类获取逻辑 4 处并行实现；Sidebar 的 `refreshTree/refreshTags` 连 AbortController 都没有（仅 mounted 标志，卸载后请求继续跑完）；DetailPage 不享受 WS 域失效的统一缓存刷新（自己注册了 useInvalidation，链路等价但重复）。
- 建议：把门禁范围扩到 `components/`；DetailPage 迁移到 `useCachedQuery`（BrowsePage 的 `['item-metadata', path, type]` 已是现成模板）。

### [P2][失效链路] useQuota 与 useFavorites 的 queryFn 不转发 AbortSignal，取消语义丢失
- 位置：`webui/src/hooks/useQuota.ts:21`（`queryFn: () => systemApi.getQuota()`）、`webui/src/hooks/useFavorites.ts:97`（`queryFn: () => favoritesApi.list()...`）
- 证据：`useCachedQuery` 的 `refresh()` 会 abort 在飞请求并重启（useCachedQuery.ts:147-152），但这两个 queryFn 丢弃了传入的 `signal`，底层 fetch 不会中止。
- 影响：身份翻转清缓存/WS 失效刷新时旧请求继续占用连接并白白消耗服务端配额；响应返回后虽被 publish 前的 abort 检查丢弃（:119,130），但网络层浪费成立。批量失效（如 orders+quota 双域事件）时浪费放大。
- 建议：两处改为 `queryFn: signal => ...` 并透传（其余 13 处使用点均已透传，属个别遗漏）。

### [P2][测试覆盖] e2e 关键缺口：真实后端验收默认 skip、axe 扫描缺 10+ 商城页面、仅 chromium
- 位置：`webui/e2e/commerce-real-backend.spec.ts:18,33`（`test.skip(!baseUrl...)`，需 `REAL_COMMERCE_BASE_URL`）；`webui/e2e/a11y.spec.ts:90-101`（ROUTES 仅 10 条，不含 /storefront/cart、/storefront/checkout、/storefront/delivery、/storefront/orders、/storefront/wishlist、/seller/orders、/seller/settings、/admin、/s/:id）；`webui/playwright.config.ts:29-31`（projects 仅 chromium）
- 证据：默认 CI 下 commerce-buyer.spec.ts（348 行）全部走 `page.route` mock；真实下单→发货→交付链路只有设置了环境变量的本地/手动运行才会验证。
- 影响：购物车数量锁、价格冲突 409 重试、交付下载幂等键（BuyerDeliveryDownloadButton.tsx:59-80 的 E5 逻辑）等关键正确性路径在默认门禁里只有 mock 级验证；键盘导航/焦点管理的商城页面无 axe 基线。
- 建议：把 a11y ROUTES 扩到全部 26 页；有条件时在 CI 加一个真实后端 job（项目自带后端，起服成本低）；补 firefox 一档。

### [P3][性能/内存] queryCache 的 gc 只重置快照，entries Map 永不删除键
- 位置：`webui/src/cache/queryCache.ts:193-203`（gc 回调仅 `leaving.snapshot = idle`，无 `entries.delete`）
- 证据：订阅计数归零后注册表删除键（:120），但条目对象（含序列化键字符串）留在 `entries` 中；`clear()` 只在身份翻转时清空。
- 影响：长会话内每个浏览过的路径/标签搜索/查询组合永久累积一个空条目；单条很小，量级为数千键/天级会话，属慢性增长非泄漏灾难。
- 建议：gc 触发时连条目一起删。

### [P3][正确性边界] useCachedQuery 错误快照回写 pre-flight 的 previous.data，可回滚中途的乐观更新
- 位置：`webui/src/hooks/useCachedQuery.ts:104`（`const previous = current.snapshot`）与 `:134-139`（错误分支 `data: previous.data`）
- 证据：`previous` 在请求发出前捕获；若请求在飞期间 `setData()` 写入了乐观补丁（BrowsePage.tsx:339-348 的 notes 乐观写），随后请求失败，错误快照会把 data 拉回 pre-flight 版本，乐观结果丢失。
- 影响：仅"在飞+乐观写+失败"三条件叠加时可见（notes 场景 save 失败后会 toast 报错并回滚，用户感知为编辑丢失）。低频边界。
- 建议：错误分支读取 `current.snapshot.data` 而非闭包 `previous.data`。

### [P3][i18n] 硬编码英文 UI 字符串残留
- 位置：`webui/src/components/layout/InfoPanel.tsx:139`（"Loading preview" 及 aria-label）、`:141`（"Preview unavailable"）、`:147`（aria-label="Loading inspection details"）、`:135`（`Open ${selected.name} preview`）；`webui/src/pages/LandingPage.tsx:485`（sr-only "Library unavailable"）
- 证据：三语字典 605 键完全对齐，但这些字符串未入字典，zh/ja 用户会看到英文。
- 影响：中/日界面局部英文字样；屏幕阅读器标签不随语言切换。
- 建议：补 4-5 个键进三语字典。

### [P3][性能] StatusBar 10s 轮询不感知页面可见性
- 位置：`webui/src/components/layout/StatusBar.tsx:33`
- 证据：`setInterval(load, 10000)` 无条件运行；服务不可达时每 10s 一次失败请求（客户端还会各自重试 3 次 GET，被 10s 节流兜住，不构成风暴）。
- 影响：挂后台的标签页持续产生 `/api/stats` 请求；多标签页叠加。
- 建议：`document.hidden` 时暂停，`visibilitychange` 恢复时立即刷一次。

### [P3][失效链路] BrowsePage 1.5s 手动刷新抑制窗吞掉并发外部事件
- 位置：`webui/src/pages/BrowsePage.tsx:397`（`if (Date.now() - lastManualRefreshRef.current < 1500) return;`）
- 证据：注释已自认风险（"only risks swallowing a genuine change from another client that lands within it"）。
- 影响：本机改标签后的 1.5s 内，其他客户端的任意 files/metadata/tags 失效被跳过，需等下一个事件。
- 建议：抑制窗按 path/domain 精确匹配而非全量跳过，或缩短至只去重同源事件。

### [P3][已知退化] AuthContext 连接失败（非 503/network）静默降级为 guest
- 位置：`webui/src/stores/AuthContext.tsx:176-189、196-206`（B6 注释自述"degraded"）
- 证据：`/api/system/info` 返回 500 时仅 `console.error`，UI 落到 guest 视图，`serviceUnavailable` 不置位，LandingPage 不会给出重试界面。
- 影响：后端 5xx 被呈现为"无权限的访客态"，用户困惑。
- 建议：增加 `connectError` 状态并让 LandingPage 消费（代码注释已规划，缺 UI 消费者）。

### [P3][卫生] permissions 死字段保留在 AuthState
- 位置：`webui/src/stores/AuthContext.tsx:29-37、47、215`
- 证据：B7 注释明确说明该字段永远是 `[]`，仅为测试/类型兼容保留。
- 影响：新消费者可能误以为它有语义。
- 建议：迁移测试后删除。
