# 01 · 现状审计与问题清单

> 全部论断基于源码与文档取证，证据以 `文件:行号` 标注。

## 一、系统现状速览

- **插件载体**：`Plugins/Addons/{id}/plugin.json` + 入口模块（默认 `parser.py`）；另有 `RuntimeData/Shared/plugins/` 搜索路径
- **核心类**：`PluginDescriptor`（descriptor.py:64）/ `PluginRecord`（:92）/ `PluginManagerService`（manager.py:22）/ `PluginHostContext`（host_context.py:107）/ `PluginLoader`（loader.py:64）
- **贡献类型**：命令、菜单、工具窗口、文件处理器、右键菜单项、分类、列、搜索提供者、主题 token、事件钩子（host_context.py:18-103）
- **UI**：PluginManagerDialog（plugin_manager_dialog.py:348，列表 + 详情 + 开关）
- **文档**：Plugins/Docs/API.md / PLUGIN_SYSTEM.md / MODULE_INTERFACES.md

## 二、问题清单（按严重度排序）

### P1 [严重] 入口协议五套并存，文档只描述其中一套

`PluginLoader._build_instance`（loader.py:76-98）支持：
1. 入口是**类** → 实例化
2. 入口对象有 `register/unregister` → 直接用
3. 入口是 **callable** → `_CallableAdapter` 包装
4. 模块有 `match/parse` → `_FunctionAdapter` 包装（文件解析器专用）
5. `entry: "parser.py"` 无 `:object` → 取模块本身（第 4 套的变体）

而 **Plugins/Docs/API.md 只描述了第 4 套**（"The entry module must define these two functions: match/parse"）——文档、示例（booth_link）、代码能力三者脱节。**插件作者无从得知"哪种写法是对的"**——这就是"定义模糊"的第一个根源。

### P2 [严重] "文件解析器"是特化协议，与通用贡献模型并列

- `_FunctionAdapter` 的 `match/parse` 协议绕过 `PluginHostContext`，由 `PluginManagerService.parse_file`（manager.py:234-273）直接遍历 `record.plugin_instance` 的 match/parse 属性
- 同一插件**可能双路径执行**：若插件既用模块级 `match/parse`（走实例属性路径），又在 register 里调 `register_file_handler`（走 host 注册表路径，manager.py:249-264），同一文件被解析两次
- `display_fields`（manifest 声明）与 `parse()` 输出（dict）的关联**没有校验**：parse 返回的 key 不在 display_fields 里 → 静默丢弃；display_fields 声明的 key 永远不产出 → 显示空值（info_controller.py:215-226 消费侧无任何校验）

### P3 [严重] 无运行时上下文（Blender 的 bpy.context 缺失）

`PluginHostContext` 的 `_current_root_path` / `_selected_paths` 在**构造时定格**（host_context.py:112-116），`get_current_root_path()` / `get_selected_paths()`（:398-404）返回的是注册时的快照。

- 插件**无法在执行时获知**：当前库是哪个、当前选中了哪些文件、当前浏览目录——除非通过 `when(file_path)` 的单个路径参数（右键菜单项）或命令 handler 的显式传参（面板路径 _actions.py:118-122）
- 全局命令路径（window.py:618-638 `_run_plugin_command`）调用 `handler()` **零参数**——同一命令，从工具菜单执行拿不到文件，从右键菜单执行拿得到。两条执行路径语义不一致

### P4 [严重] 权限系统是纯样子货（死代码）

- `ALL_PERMISSIONS` 定义齐全（descriptor.py:22-44）、`check_permission` / `_check_permission_warn` 存在（host_context.py:314-332）
- 但 **`granted_permissions` 从未被赋值**：bootstrap 创建 `PluginHostContext()`（bootstrap.py:110）不传参数 → 恒为 `frozenset()`
- 后果：`check_permission` 永远返回 False；`_check_permission_warn` 只打 warning 不阻止（host_context.py:326-332）——**权限声明零效果**，且给插件作者"我的权限声明生效了"的错觉

### P5 [严重] 两个贡献类型是死代码（注册了但无消费点）

| 贡献 | 证据 |
|---|---|
| `ToolWindowContribution` | 仅 host_context.py 内部定义/注册/查询，**全仓库无任何 UI 消费** `tool_windows()` |
| `Category` / `ThemeToken` | `apply_registered_categories`（manager.py:290）与 `apply_registered_theme_tokens`（manager.py:324）**无任何调用者**——分类注册了但过滤下拉/搜索永远看不到 |

### P6 [严重] 注册 API 风格不统一（dict vs 位置参数）

```python
register_command(descriptor: dict, handler)          # dict
register_menu_contribution(descriptor: dict)         # dict
register_tool_window(descriptor: dict, factory)      # dict
register_file_handler(plugin_id, match, parse)       # 位置参数
register_context_menu_item(plugin_id, item_id, label, command_id, ...)  # 位置参数
register_category(plugin_id, key, label, extensions) # 位置参数
register_column(plugin_id, key, label, ...)          # 位置参数
register_search_provider(plugin_id, provider_id, ...) # 位置参数
register_theme_token(plugin_id, token, fallback)     # 位置参数
hook(event_type, handler, plugin_id)                 # 位置参数
```
（host_context.py:133-308 全部）——**没有一致的"注册签名"心智模型**，每个方法都要看文档。

### P7 [中等] manifest 字段悬空（文档声称的字段代码不解析）

- `provides`：API.md 声称是能力标签，`PluginDescriptor` **从未解析该字段**（descriptor.py:64-89 无此字段）——download_tracker/plugin.json 里写了 `"provides": ["info.fields", "file.metadata"]`，纯装饰
- `config_schema`：API.md 声称"Future: settings schema"，**不存在**
- `kind`：解析了（descriptor.py:71）但**无任何消费**——"command" vs 其他值的区别无人读取
- `permissions`：解析了但永不生效（P4）

### P8 [中等] 无插件偏好设置（Blender AddonPreferences 缺失）

插件无法声明自己的设置项；没有 `Preferences` 概念，设置对话框（settings_dialog.py 三 Tab）无插件设置页。

### P9 [中等] 无 Operator 抽象（无撤销、无参数、无 poll）

- 命令 = 无参回调；**无插件操作可进撤销栈**（UndoService 只服务 FileOperationService）
- 无 poll 机制：菜单项/命令的可用性只能靠 `when(file_path)`（右键菜单）或硬编码 `enabled: bool`（manifest）
- 无参数化执行：命令无法弹参数对话框

### P10 [中等] 生命周期不完整

- **UI 启用不立即加载**：PluginManagerDialog 的 toggle 只调 `enable_plugin`（状态→LOADABLE，manager.py:132-141），**不调用 load_plugin**——用户点"启用"后插件不生效，需重启应用（对话框无任何提示）
- **无热重载**：改插件代码需重启
- **无错误恢复 UI**：插件进入 ERROR 状态后无"重新加载"按钮
- **无依赖/版本声明**：manifest 无 `min_host_version`、无 `dependencies`

### P11 [中等] 状态双源（manifest 与 AppSettings 语义混乱）

`enabled_by_default`（descriptor.py:71，来自 manifest 的 `enabled`/`enabled_by_default`）与 `plugin_disabled_ids`（AppSettings，manager.py:112-126）双轨：`build_plugin_record` 用 manifest 初始化 enabled，discover 时再被设置覆盖——**"默认启用"与"用户禁用"无法区分**，无"恢复默认状态"能力。

### P12 [中等] 卸载的 sys.modules 清理过激

`unload_plugin`（manager.py:205-208）`del sys.modules[module_name]`：若两个插件 import 同一公共模块（如都 import `AssetsManager` 内部工具），卸载一个会破坏另一个已加载模块的引用。无插件命名空间隔离。

### P13 [低] 命令双执行路径

- window.py:618-638：全局命令 `handler()` 无参
- _actions.py:118-140：面板命令 `_run_plugin_command(cmd_id, file_path)` 带路径
- 同一 `command_id` 两套查找逻辑、两套调用签名——插件无法统一处理

### P14 [低] 插件管理器信息展示弱

PluginManagerDialog（plugin_manager_dialog.py:236-302）只展示 manifest 字段（name/version/description/display_fields/state）；无：权限声明展示、错误堆栈查看、日志、贡献清单、API 版本。

### P15 [低] 文档承诺 > 实现（三份文档均部分过时）

- PLUGIN_SYSTEM.md 描述的状态机与实现一致，但贡献类型部分（ToolWindow/Column/SearchProvider）无使用示例
- API.md 的 `config_schema`/`provides` 未实现（P7）
- MODULE_INTERFACES.md 描述的内部接口与 `core/plugins/__init__.py` 导出不完全一致

## 三、问题根源总结

1. **没有"统一注册模型"**：每加一个扩展点就加一套签名（P6）与一条执行路径（P2/P13），导致协议分裂
2. **没有"运行时上下文"**：插件无法表达"我现在要对什么操作"（P3）——这是与 Blender 差距最大的单点
3. **没有"可执行性验收"**：权限（P4）、分类/主题 token（P5）、provides（P7）都是"写了但没人接"——**每个扩展点都没有端到端测试**
4. **生命周期缺环**：启用/加载/错误恢复/热重载不闭环（P10/P11）
5. **特化先于泛化**：文件解析器（booth_link）是最早的真实需求，其 match/parse 协议被当成"插件协议"本身写进了文档——通用化从未发生

## 四、与 Blender 的差距（预告）

Blender 用**一个机制**（`register_class` 注册表 + 类属性声明）覆盖了当前系统 10 个零散注册方法的能力，用 **context 对象**解决了运行时上下文，用 **poll** 解决了可用性，用 **bl_info** 解决了元数据规范。详见 [02-Blender插件API设计启示.md](02-Blender插件API设计启示.md)。
