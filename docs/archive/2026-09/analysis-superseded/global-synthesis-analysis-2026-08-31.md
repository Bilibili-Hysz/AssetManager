## 0. 一页判定

**AssetManager 是一个"工程纪律上乘、安全基本功扎实、但存在系统性最后一公里欠账"的项目。** 三轮评审的结论高度收敛、互为印证，不存在互相矛盾的重大判断——这说明前两轮评审质量可靠，第三轮的增量发现（S2/S5/spec 陈旧）都是在既有结论的边界上**纵深扩展**而非推翻。

**三个最有决策价值的核心论断：**

1. **项目的成败取决于"极值场景"，而非中值体验。** 所有 CRITICAL/HIGH 级风险都集中在两个极值：**公网暴露**（未认证攻击者）与**十万文件规模**（磁盘膨胀、深分页、写放大）。日常 LAN + 小库场景下项目运行良好——这正是风险容易被低估的原因。
2. **P0 五项不是随机的 bug 清单，而是"局域网威胁模型 → 公网威胁模型"转换的必然补课项。** 项目安全基本功（PathGuard、PBKDF2 600k、fail-closed、SHA256 pin）是在局域网可信假设下设计的；一旦暴露面扩展到未认证互联网，假设逐一失效（限流有意义、DB 不可读、磁盘不可控、审计可见），P0 恰好是这些假设的破裂点。
3. **"最后 10%"是贯穿所有维度的主旋律。** 缩略图缓存无自动淘汰、Cython 链路断裂、pyright 排除两子系统、CI 不盖特性分支、skip 路由零限流、文件整读无上限——每个子系统都做到 90%，缺失的 10% 恰是极值场景的决胜点。

**评级汇总（三轮一致）**：

| 维度 | 第一轮 | 第三轮 | 收敛判断 |
|---|---|---|---|
| 架构 | B | B+ | 分层骨架良好，DI/依赖方向/总线为欠账 |
| 工程质量 | B- | B+（近 A-） | 纪律强，扣分在构建链与类型盲点 |
| 安全（局域网） | B+ | C+（公网前提） | 基本功扎实；暴露面升级后 C+ |
| 性能 | B- | B- | 交互优秀，规模承载受限于 P1/P2/P5 |
| 功能/双端 | B- | B（UX） | 双端奇偶差与 Web 缺撤销为硬缺口 |

## 2. 五大系统性根因（跨维度主题）

单点风险可以逐个打补丁；**系统性根因必须从机制上治理**，否则补丁只是下一个风险的前奏。

### T1：文档-代码系统性背离（信任债）

**证据群**：商城 54 路由纸面化（`README.md:206`）；spec 幽灵 shop 模块（`AssetManager.spec:177-182`）；spec 大小写 `Assets/` vs `assets/`（`spec:77`）；upload 废弃仍展示（`dto.py:103`、`sidebar.py:105`）；仓库数量口径矛盾（README 50→17 / 84→12）；Cython 加速声明未兑现（`setup_cython.py` vs `build.py`）；暴力锁定声称"5 次/60s" vs 实际 10/300s。

**影响**：README 从"事实记录"退化为"营销文案"，对外承诺失真；构建配置（spec）静默腐烂，靠 `check_package_contents.py` 在 CI 兜底；新成员 onboarding 依据失真。

**根因**：项目有成熟的"验证边界"文化（`README.md:10`），但**只对测试生效，不对文档与构建配置生效**——文档被当作散文而非代码管理。功能的增删（商城规划→废弃、upload 下线）没有同步触发文档与 spec 的更新流程。

**治理方向**：① 把 spec 的 hiddenimports 改为**从模块图生成**（消除手工枚举漂移，spec:88-294 的 100+ 条目即漂移源）；② README 的功能宣称加"状态标记 + 最近验证日期"，并扩展 `check_doc_stats.py` 覆盖功能宣称；③ 废弃功能走统一下线流程（删除 DTO 声明 + spec 条目 + README 条目，三处同 commit）。

### T2：安全姿态与暴露野心错位（威胁模型滞后）

**证据群**：全部 P0 项 + R7（隧道下白名单绕过）+ S2/S5 的"未认证可触达"属性。

**关键洞察**：项目安全基本功之强（路径纵深、PBKDF2 600k、fail-closed、令牌撤销持久化、隧道 SHA256 pin）说明**不是忽视安全，而是威胁模型按"局域网可信"设计**。局域网上：per-IP 限流有意义、DB 不可被外人读取、磁盘空间不被攻击者控制、"审计日志"可见。一旦打开 Cloudflare 隧道——上述假设全部失效：限流可被多 IP 打穿、DB 可被旁路读取、guest 可刷图片预览耗内存与磁盘、错误可被枚举。

**影响**：安全评级在"局域网 B+"与"公网 C+"之间的落差，正是假设失效的量化体现。

**治理方向**：① 维护一份**正式威胁模型文档**（资产/信任边界/攻击者画像），每次新增分享面能力（隧道、guest、匿名、新路由）强制走威胁模型复审；② 把"未认证路径"作为 CI 的**专项 fuzz 面**（随机 token、超长路径、巨文件、并发突发）——未认证攻击面测试应独立于功能测试；③ P0 方案落地后，补一条"假设检查清单"回归测试，锁定"局域网假设→公网假设"的转换点。

### T3：广度优先 vs 最后一公里（中值优化，极值欠账）

**证据群**：U-6（缩略图缓存无淘汰）、U-16（Cython 断链）、U-10（类型盲点）、U-15（CI 不盖分支）、U-2/U-3（skip 零限流、整读无上限）、U-24（每目录 fsync）。

**关键洞察**：三轮评审的性能结论高度一致——**交互体验（浏览、搜索、缩略图）在万级文件下优秀，所有失败点都在极值**：磁盘无限膨胀、深分页退化、批量导入写放大、未认证突发。项目擅长把"中值场景"打磨到 95 分，对"尾部场景"只做到 60 分，而**尾部场景恰是用户规模增长与暴露面升级的必然路径**。

**治理方向**：为每个子系统的"资源生命周期"建立闭环心智——缓存必须有配额与淘汰（U-6）、请求必须有预算与上限（U-2/U-3）、写路径必须有批处理与异步（U-24）、构建声明必须接入构建（U-16）。**建议新增一条架构审查原则：任何"无限增长/无限消耗"的路径（缓存、读入、请求、并发）在合并前必须有上限与降级。**

### T4：双端双实现的内在成本（DRY 违反的结构化）

**证据群**：校验常量三处硬编码（notes 4000：`metadata.py:30` vs `InfoPanel.tsx:173` vs `DetailPage.tsx:242`；rating 0-5 双写：`metadata_service.py:335` vs `routes/metadata.py:154`）；DTO 双源（生成的 `contracts.ts` 与手写 `api.ts` 并存）；i18n 双 key 体系（桌面 `filelist.sort.name` vs Web `sort.name`）；功能奇偶差（Web 无撤销/排序缺 type/无缩略图尺寸）。

**关键洞察**：双端是本项目的差异化优势（也是与 Serpent 的分水岭），但每个新功能都产生 2 倍实现成本与持续漂移。项目已有的 **DTO 契约代码生成 + CI drift 门禁**（`contracts.ts` 自动生成，`ci.yml:29`）证明团队已找到正确解法——只是**只覆盖了 DTO 层，没覆盖校验常量、i18n、错误码**。

**治理方向**：把契约生成从"类型层"扩展到"约束层"——经 `/api/system` 元数据下发校验常量（对齐 A7 建议）；i18n 抽共享 key 目录（对齐 U6）；`api.ts` 与 `contracts.ts` 二选一。每新增一个双端功能，把"两端各写一遍的规则"作为 code-review 红线。

### T5：架构承诺与实态落差（名义分层 vs 实际拓扑）

**证据群**：DI 自述"simple service locator"（`di/__init__.py:3`），container.resolve 仅 8 处全在 bootstrap 内部，业务代码靠 74 处 AppSettings.instance + 27 处 get_event_bus 拉取；domain→core 反向依赖（`domain/events.py:11`）；transport 层直读 AppSettings（`metadata.py:371`）；God-object window.py 绕过分层（`window.py:1248`）；桌面分享经 loopback HTTP 而非服务直调（`_share_api.py:21-60`）。

**关键洞察**：**架构骨架是好的**——每库会话隔离（session_token + epoch/revision 双过滤）、Port/Protocol 窄接口（`desktop_ports.py:20-40`）、事件桥接线程纪律、防御性关闭协议，这些是 B+/A- 级设计。问题在于**承诺未兑现**：README 宣称的 DI/分层是"名义架构"，实态是"服务定位器 + 单例 + 少数干净接缝"。名义与实态的落差让重构成本高企——开发者不知道哪条依赖是真实的。

**治理方向**：优先做**低成本高信号**的修正——domain→core 反向依赖（U-19，把 DomainEventBase 下沉进 domain，单文件改动）；bus 直订阅改走带 token 过滤的订阅（U-11）；runtime 缓存键改 session.event_token（第三轮 A5，防 id() 复用）。DI 实质化（U-18）工程量大、收益渐进，建议排 P2 并在拆分巨型文件时顺带推进。

## 3. P0 方案批判性评审

对 `docs/plans/p0-security-remediation-2026-08-31.md` 的整体评价：**质量高、可执行**——证据精确到行、波及面核实到位（P0-4 确认仅 4 处调用点）、验收门禁含对抗性用例（伪造测试、恶意插件夹具、OOM 断言）。以下是指出**方案自身的边界与残留风险**，供实施时补强。

### P0-1 插件信任列表（阶段 A）

- ✅ 亮点：`trusted` 字段 + SHA-256 指纹 + "信任并启用"二次确认 + 未信任插件仅走纯函数路径，是成本最低的"默认不信任"落地；阶段 B（subprocess）与 Serpent 双档运行时思路对齐。
- ⚠️ 边界：**信任列表不是隔离**。安装流程本身（用户在插件管理器导入）就是社工向量——恶意插件的指纹在"安装"那一刻被登记为"可信"。阶段 A 把威胁从"任意插件"缩小到"用户明确信任的插件"，但**阶段 B 不可拖延**，应作为 P0 的组成部分而非"1-2 迭代后"。
- ❌ 遗漏：① 插件**更新**后指纹变化——必须有"更新即重新信任"的流程，否则静默拒绝或静默放行都不可接受；② **撤销信任**路径（如何 untrust 已信任插件）；③ 自动发现（`Plugins/Addons/` 与 `RuntimeData/Shared/plugins/`）在阶段 A 是否默认关闭未明确——建议默认关闭，仅显式导入。

### P0-2 skip 限流兜底

- ✅ 亮点：方案 A（media 档 2000/60s/IP）+ 方案 B（格式预检 + 失败计数桶）叠加正确——**方案 B 才是 load-bearing**，A 是纵深。
- ⚠️ 边界：① media 档 2000 次/分钟/IP 仍允许每 IP 每分钟 2000 次 PBKDF2（约 40-100ms/次 ≈ 单个攻击 IP 可持续占用近 1 核）；合法格式但错误的 token 不受格式预检拦截，仍吃 PBKDF2——**失败计数桶必须按 IP 限速在 PBKDF2 之前**（方案已含，实施时注意桶的淘汰策略与内存上限）；② `/ws` 长连接不适合按请求计费，方案在"遗留"中已注明需帧级预算——这是 skip 类中唯一真正需要保留的豁免，建议给出明确结论（帧级预算 or 握手后断开重连）。
- ✅ 补充建议：与 U-3（OOM）联动——media 限流与大小上限同时落地后，未认证攻击面的两个突发向量同时关闭，验收时做组合测试。

### P0-3 流式化 + 大小上限

- ✅ 亮点：复用 `read_snapshot` 已有的 `max_bytes`（`file_snapshot.py:186-190`）是最小改动路径；流式发送后 fstat 复核 identity（对齐 `read_snapshot:192` 防换文件）保留了既有安全语义；quota 后置计数与断连清理模式复用既有代码（`downloads.py:123-126`）。
- ⚠️ 边界：① 512MB/256MB/512MB 上限是**产品策略**而非纯安全参数——单文件下载 413 对合法大文件用户是体验损失，建议上限进 `lan/constants.py` 并暴露为可配置项（方案"遗留"已提）；② 图片解码路径 256MB：16-bit 8K 图可超限，413 而非降采样是行为变化，需在 webui 有对应错误呈现；③ 未利用这次改造顺带加 HTTP Range（视频拖动/断点续传的前提，U-22）——成本相近，建议同 commit 内评估。

### P0-4 密码令牌独立密钥

- ✅ 亮点：波及面核实为单点（4 处调用）、分享令牌与 user/local_ui 令牌独立不受影响、不做旧格式兜底（24h 一次性切换）——**判断正确**：旧格式兜底反而保留伪造窗口。
- ⚠️ **两个被低估的副作用**：
  1. **语义回归**：当前实现"改密码 → key 轮换 → 旧令牌全体立即失效"；改造后（内存密钥与密码无关）**改密码不再踢出旧会话**，24h 窗口内被盗令牌仍有效。方案只在文档说明，但这是**安全语义的倒退**——建议在令牌负载中加入 `pwd_version`（用户表加计数器），验证时比对，恢复"改密即失效"属性，成本极低。
  2. **重启风暴**：内存密钥（不落盘）意味着每次应用重启所有登录用户重新登录——LAN 服务器内嵌在桌面应用里，桌面应用重启频率高（dev 构建更甚），用户体验是"频繁被踢"。建议改为从既有 `token_secret`（`bootstrap.py:685` 已每次启动生成）经 HKDF 域分离派生 `password_token_secret`——同样是重启轮换，但密钥管理单点化，且未来若要持久化只需改一处。
- ❌ 遗漏：验收门禁缺"改密码后旧令牌失效"用例（对应上述语义回归）；缺"重启后所有旧令牌失效、用户需重登"的行为标注。

### P0-5 匿名裁剪 + 默认绑定

- ✅ 最干净的一项：匿名分支保留 login/landing 页依赖的字段、移除 library_root/library_stats；`auth=none` 默认 127.0.0.1 + 显式开关。webui LandingPage 联动说明到位。
- ⚠️ 微瑕：R7（隧道下白名单绕过，`security.py:269`）不在本方案内——P0-5 处理了"默认绑定"却没处理"白名单语义误导"，后者是纯文档/日志告警项，建议并入本 commit 顺手完成。

### 方案遗漏项（不在 P0 范围内、但值得提请注意）

- **U-6 缩略图缓存**：严格说是"磁盘填充 DoS"的近亲——如果 guest 可刷大量缩略图请求触发烘焙（`thumbnail_service.py:441` 写入路径无配额），配合未认证面可被用于撑爆磁盘。建议与 P0 同迭代把"bake 尾部自动 enforce"（P1 建议）提前。
- **S6 ZIP worker 并发配额**：2 个 worker 被并发打满即 DoS（`server.py:104-106`），成本低，建议并入提交 1。
- **R8 配额双账本**：功能一致性而非安全项，保持 P1 即可。

## 4. 决策框架：三扇门

| 门 | 判定问题 | 门槛项 | 时间 |
|---|---|---|---|
| **门 1：公网暴露** | "能否允许 Cloudflare 隧道对外？" | U-1..U-5 全部落地 + 上述批判性补强（P0-4 语义回归、S6 并入） | 1–2 周 |
| **门 2：规模承载** | "能否平稳服务 10 万文件库？" | U-6（缓存淘汰）+ U-7（写并发/分页）+ U-24（批量 fsync）落地，并加 **10 万库基准测试为性能门禁**（当前 perf 测试 opt-in 且 continue-on-error） | 1–2 月 |
| **门 3：工程深化** | "可维护性是否进入 A 级？" | U-8（spec 生成化）、U-10（pyright strict）、U-15（CI 盖分支）、U-18/19（DI 收敛）、巨型文件拆分 | 持续 |

**关键提醒**：门 1 与门 2 相互独立、但都不可跳过。**只做门 1 不做门 2** 的结果是"公网可用但 10 万库卡死"；**只做门 2 不做门 1** 的结果是"本地流畅但公网裸奔"。三轮评审里最容易犯的决策错误是把两者混为一谈（例如用"本地好用"论证"可以发布"）。

## 5. 战略层面：与 Serpent 对照的再审视

第二轮功能对照的结论（AM 的分享/Web/权限体系 vs Serpent 的沙箱/采集/同步广度）本报告完全认同，补充三点研判：

1. **差异化的代价就是风险面**：AM 的差异化优势（LAN 分享 + Web + 隧道）**恰好就是**其风险面（未认证可达 + 公网暴露）。这不是矛盾，而是产品定位的自洽——但意味着 AM 的**安全投入必须系统性高于** Serpent 这类"本地优先"产品。Serpent 不需要解决未认证攻击面，AM 必须。**安全预算应被视为差异化的运营成本，而非负担。**
2. **借鉴的顺序有依赖**：Serpent 借鉴清单（智能合集/3D 缩略图/WebDAV/云 AI）都是功能层收益，但**插件沙箱（U-1）是工程前提**——不先解决执行隔离就引入更多插件能力（云 AI 适配器、扩展采集），是在扩大 RCE 半径。功能借鉴必须排在门 1 之后。
3. **"不照搬"的论证成立**：Serpent 无远程分享是其定位选择；AM 复制 Serpent 的"本地优先"路径等于放弃核心差异。正确的姿态是**单向借鉴 + 保持差异**：把 Serpent 的隔离与广度能力移植进 AM 的分享定位里。
