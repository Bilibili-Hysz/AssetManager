## 2. 八个跨域主题

### 主题一：验证承诺与现实的鸿沟（最高优先）
项目最大的差异化资产是"证据文化"（dated manifest、fixed-unverified 纪律、8 个自研门禁），但它建立在"门禁会真实运行"的前提上——而这个前提当前不成立：仓库无 remote（CI 从未执行过一次）、CI 触发只限 master/main（当前质量审计分支的 172 处变更零验证）、release 不依赖任何测试结果、唯一有阈值的性能门禁被默认排除。这不是产品缺陷，而是**质量承诺的兑现风险**：README 描述的矩阵全部是纸面状态。若不先修复这一层，其余 127 条发现的"修复"同样无法被验证闭环。

### 主题二：数据安全边界的四个单向窗口
产品代码中最接近数据丢失的四个点都在"失败路径的后半段"：`restore_backup` 失败清理会删掉已存在的目标文件（02-P1）；settings.json 遇到未来版本拒绝迁移却不隔离写入，首次 `set()` 即整体覆盖（04-P1）；导入意图清单的恢复态没有终态，每次开库重复全库重扫（02-P1）；restore 的 quarantine→install 两步替换间崩溃后库静默变空（02-P2）。共同模式是"前半段的防御（拒绝、校验、隔离）做了，后半段（写入防护、终态、回滚）缺一口气"。

### 主题三：并发与时钟假设不统一
- **两代事务模式并存**：~65 个写方法走 SAVEPOINT 助手，27 个仍是裸 `commit()`（19 个无条件提交调用方事务）——事务撕裂的潜伏面（05-P1）。
- **读-改-写窗口**：`ShopRepository.update_item` 合并读取在事务外（05-P1，一行修复）；`remove_url` 跨连接丢更新（05-P2）；`metadata_repository` 同类问题已修而它没跟进。
- **时钟假设**：对账队列 lease 判定、TTL 缓存、限流窗口全部依赖墙钟，时钟回拨产生双 worker 或缓存雪崩（02-P2、04-P3）。
- **锁纪律不对称**：`ProjectData` 读路径绕过连接写锁（04-P1）；跨连接写锁嵌套无锁序防护（04-P1 疑似）；事件在持有路径锁时同步分发（02-P2）。

### 主题四：缓存治理分散
同表相邻两列采用两套失效策略（`cached_size` 有 mtime+TTL 双保险，`cached_file_count` 三无——03-P1）；gallery 增量与全量重建的 generation 竞态丢窗口期事件（03-P2）；TagService 路径缓存永不失效、thumbnail 服务缓存模块级跨库共享、TTL 全用墙钟。根因是**没有统一的缓存失效契约**（写路径清单、事件驱动失效、预算上限），49 处缓存各自为政。

### 主题五：巨型模块与隐式协议网
file_list 的 5+3 mixin 星系靠约 200 行 `TYPE_CHECKING` 存根互相"签约"（运行时零校验）；跨模块私有访问密集（`server._port`×3、`file_list._loader`、`grid._scrollbar`×6+、`_path_locks` 等），AST 门禁不拦 presentation 内部耦合；`host_context` 单类 1569 行揉了身份/权限/八种注册表/undo/通知。项目自己的债务报告（13 号文档）列出的 20 个 >1000 行模块中，本轮确认拆分收益最高的 7 个全部复现于各域文档的"规模观察"节。

### 主题六：公网暴露面的加固尾款
LAN 代码本身的安全工程扎实（无 P0），但 **Cloudflare 隧道开启后安全模型退化**：全部公网流量共享 127.0.0.1 速率桶（认证 DoS 单点，06-P1）；cookie 无 Secure 标志（06-P3）；`Cf-Connecting-Ip` 未被利用。叠加密码模式令牌以落盘哈希为 HMAC 密钥（06-P2）、无邀请码时注册完全开放（06-P2）、cloudflared 下载无哈希校验（06-P2 + 08-P0），"从 LAN 到公网"这一步的设计假设（回环可信、同网段用户可信）没有被系统性地重新审视。

### 主题七：平台语义盲区
生产平台是 Windows，全量测试却在 ubuntu 跑：junction 测试在 CI 两个 lane 都不执行、symlink 以 POSIX 语义测而生产是特权+混合语义、WinError 5/1314 行为只有本地覆盖（08-P1）。叠加 flaky 测试靠口头约定"不算回归"（08-P1）、`_cleanup_stores` 只清 2 个全局点而生产有 15+ 处（08-P1），"测试绿"的含金量在平台维度被稀释。

### 主题八：前端单源化的长尾
S1-S5 收敛是真实的，但门禁只扫 `pages/`（Sidebar 绕过）、类型存在双源（api.ts 手写复制 5 个生成 DTO）、卖家域三个页面两个用错客户端（卖家 401 级联登出主会话，07-P1）、下载超时实现与语义不符（07-P1）。模式与主题一同构：**单源规则的覆盖边界小于规则的声称为**。

## 4. 修复纪律建议

按本仓库既有证据文化执行：

1. **每项修复附带回归测试**再标记状态；修复后在本目录对应领域文档的发现条目追加 `fixed (commit, date)` 注记，但不改变 `fixed-unverified` 语义——全量验证证据仍走 `docs/full-review/` 的 dated manifest 体系。
2. **第一批 9 项里 4 项是一行级改动**（#2/#4/#6/#8），建议单独成一个小 commit 批次先落地，立即消除最高风险。
3. 第二批安全项修复后，建议在 `lan-security.md` 或 full-review 体系补一份"公网暴露模型"文档，把隧道场景下各机制的信任假设显式化（当前散落在代码注释里）。
4. 本审计的行号锚点会随后续提交漂移；引用时以符号名（函数/类）为准。
