# AssetsManager 全量扫描审计报告（2026-08-20）

## 1. 结论摘要

本报告记录本轮对 AssetsManager 的分模块全量静态扫描结果。审计覆盖桌面端、核心应用服务、LAN/API、文件与媒体服务、WebUI、国际化、数据库与并发、测试、CI、发布、依赖和文档。

**总体结论**：未发现可静态确认的 P0 问题；发现多项 P1/P2 风险，其中最高优先级集中在：

- 分享预览绕过图片内容验证和隐私模糊策略。
- 路径检查后按路径重新打开文件，存在 symlink/TOCTOU 窗口。
- 未配置认证时媒体路由可匿名访问，并使用 `skip` 速率策略；媒体处理缺少统一 CPU、像素、并发和磁盘预算。
- LAN handler 在事件循环中同步执行 PBKDF2、SQLite 查询和提交。
- POSIX stale lock 恢复存在跨进程 unlink 竞态。
- token 撤销持久化失败后可能在重启/新实例中 fail-open，且撤销数据库操作没有完整纳入 session lease。
- 发布工作流没有执行完整回归和 frozen runtime 验收；Python 依赖不可复现，Actions 未固定 SHA，真实 Commerce 默认跳过。
- WebUI 存在 key 登录凭据残留在 URL、查询缓存旧响应覆盖新 key、认证 generation 竞态等问题。

**本次没有执行**：生产代码修改、测试执行、服务启动、网络黑盒测试、压力测试、依赖安装、提交或发布。桌面组仅进行了测试收集（`--collect-only`），不代表行为测试通过。因此，涉及实际 RSS、事件循环延迟、平台文件锁和代理缓存的结论仍需按报告末尾的验证矩阵复核。

## 2. 审计方法与分组

本轮按细分模块分批执行，默认顺序执行，互不依赖的组最多并行两个。每组使用只读子代理，统一要求提供文件、单行号、调用链、触发条件、影响和验证边界。

1. **路径与文件访问**：PathGuard、FileResponse、图片、缩略图、分享、下载、ZIP、缓存和 symlink。
2. **认证与会话**：用户、seller、分享密码、token/cookie、撤销、middleware、WebSocket。
3. **媒体与资源耗尽**：Pillow、ffmpeg、批量接口、搜索、分页、gallery、home/tree、限流、临时文件。
4. **路由策略与数据库**：aiohttp policy 生命周期、SQLite 锁、session lease、迁移、LibraryLock。
5. **业务应用服务**：share、commerce、项目、metadata、配额、插件状态机和公开 DTO。
6. **桌面端**：file list、image viewer、导航、异步任务、watcher、缩略图、国际化和当前未提交改动。
7. **WebUI 与国际化**：请求缓存、认证状态、URL、下载、CSS、i18n、E2E mock 和可访问性。
8. **工程治理**：测试、skip、coverage、类型/Lint、依赖、CI、release、SBOM、许可证和文档基线。

严重度含义：

- **P1**：高影响安全、可用性、一致性或发布门禁问题，应优先修复。
- **P2**：中等影响或需要特定部署/并发/输入前提的问题。
- **P3**：低影响、硬化建议、产品策略或维护性问题。
- **条件性**：需要产品意图、部署方式、平台能力或黑盒实验确认，不作为无条件漏洞描述。

## 3. 已确认问题

### P1-01 分享预览绕过内容验证和隐私模糊策略

- **置信度**：高。
- **位置**：`D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\lan\routes\shares.py:356-387`。
- **证据与触发**：`handle_share_preview()` 仅检查分享存在、过期、`allow_preview`、密码 token 和 `_SAFE_IMAGE_EXTS` 后缀，随后直接 `web.FileResponse(target)`。该路径没有复用 `image.py` 的 Pillow `Image.verify()`、实际格式检查、`should_blur_target()` 或 `serve_blur_gated_raster()`。
- **影响**：带图片扩展名的任意非图片内容可被当作预览返回；带隐私 blur tag 的原图可直接返回，绕过既有 fail-closed 模糊策略。密码分享还存在 URL 不含 token 的缓存风险（见 P2-03）。
- **建议**：统一复用已验证图片响应；至少执行受限 Pillow 验证、实际 MIME 检查和 blur gate。模糊失败必须拒绝，不得 fallback 原图；密码分享使用 `private, no-store`。

### P1-02 路径检查后重新打开文件导致 TOCTOU/symlink 窗口

- **置信度**：高（触发需要本地可写库目录或并发文件替换能力）。
- **位置**：`D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\lan\path_guard.py:72-118`；代表性调用点：`D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\lan\routes\downloads.py:136-168`、`shares.py:294-308,375-387`、`thumbnails.py:51-78`、`lan\routes\_helpers.py:525-568`。
- **证据与触发**：`PathGuard.resolve()`/`assert_under_root()` 通过 `Path.resolve()` 检查 containment，之后 `FileResponse`、Pillow、`zf.write()` 再按路径打开。二次 `assert_under_root()` 可缩短窗口但不是原子 no-follow；验证 A 后交换为 symlink/父目录后可能读取 B。
- **影响**：本地攻击者或共享目录中的并发写者可能让服务读取库外文件；图片验证 A、传输 B；ZIP 可能写入库外内容。
- **建议**：Linux/macOS 使用目录 FD、`openat`/`O_NOFOLLOW` 和已打开 FD 流式响应；Windows 使用句柄、拒绝 reparse point，并在最终打开后做 `fstat`/身份复核。ZIP 应以受信句柄遍历，不能以路径 `zf.write()` 作为最终边界。
- **边界**：Windows NTFS junction/reparse 和 POSIX symlink 语义不同，必须分别实测。

### P1-03 项目/首页/树扫描跟随库内 symlink，泄露库外元数据

- **置信度**：高，但前提是库目录允许普通用户或外部流程放置 symlink。
- **位置**：`D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\application\project_service.py:290,401,411,663`；入口 `D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\lan\routes\metadata.py:215,230,246`。
- **证据与触发**：`DirEntry.is_dir()`、`os.scandir()` 默认跟随 symlink；初始请求路径虽经过 `validate_path()`，但递归扫描出的子目录没有逐项 `is_symlink()`/realpath containment。`_entry_to_item()` 还会读取目标目录图片、mtime、大小、文件计数、标签等。
- **影响**：具有 browse 权限的 LAN 用户可从 `/api/projects`、`/api/tree`、`/api/home` 获取库外目录名、统计、mtime 或缩略图元数据。下载路径的 PathGuard 不能撤销已经发生的枚举泄露。
- **建议**：扫描时显式跳过 symlink/reparse；每个候选项在 `stat/scandir` 前后做 root containment；固定扫描根并处理竞态。
- **验证**：库内链接到库外 sentinel 目录，分别请求 project/tree/home，确认外部名称、统计和缩略图均不出现。若生产库由可信管理员独占写入，按部署前提降级，但仍建议 fail-closed。

### P1-04 媒体路由使用 `skip`，未配置认证时可匿名高频消耗资源

- **置信度**：高（匿名条件与资源处理行为均由代码确定）。
- **位置**：`D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\lan\api.py:274-290,320,393`；限流逻辑 `D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\lan\security.py:164-237`；guest 默认能力 `D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\lan\principal.py:93-99,135-136`。

### P1-05 输入图片缺少像素/解码资源预算

### P1-06 LAN 视频抽帧缺少专用并发预算和 single-flight

- **置信度**：高（并发控制静态缺失；实际子进程峰值需压测）。
- **位置**：`D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\application\thumbnail_service.py:239-245,268-285`；入口 `D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\lan\routes\thumbnails.py:38-64`。
- **证据与触发**：每个 cache miss 在 `asyncio.to_thread()` 中调用 `subprocess.run(ffmpeg, timeout=30, capture_output=True)`；LAN 没有独立 ffmpeg semaphore，同一 frame key 没有 single-flight/原子写。
- **影响**：不同视频或同一视频并发请求可启动大量 ffmpeg，竞争 CPU/磁盘并重复写同一 JPG；超时是单任务限制，不是全局预算。
- **建议**：服务级 bounded ffmpeg executor/semaphore、key-level single-flight、进程登记和可控终止；唯一临时文件完成后原子替换。
- **验证**：记录子进程数、超时后进程树、同 key 并发输出完整性和缓存目录状态。

### P1-08 LAN 密码和同步 DB 路径阻塞事件循环

- **置信度**：高。
- **位置**：用户登录 `D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\lan\routes\auth.py:19-75`；seller 登录 `D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\lan\routes\seller_auth.py:48-59`；分享密码 `D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\lan\routes\shares.py:230-247`；代表性认证查询 `D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\lan\server.py:1481-1495,1604-1633`；生产 PBKDF2 `D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\domain\auth.py:115-125`；SQLite timeout `D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\core\database.py:892`。
- **证据与触发**：用户名登录、简单密码登录、seller 登录和分享密码验证直接执行 600k PBKDF2；成功旧 hash 还会同步重哈希和写库。注册会先 hash 再 authenticate，可能连续执行两次。认证 cache miss、logout、users/tags/shares/shop/catalog/info 等 handler 也直接调用同步 session-bound SQLite 服务；busy timeout 可长达 30 秒。access-key 分支已经使用 `asyncio.to_thread()`，但不覆盖上述路径。

### P1-09 POSIX stale lock 恢复存在双恢复者 unlink 竞态

- **置信度**：高，但仅针对 POSIX 多进程；Windows 不应外推。
- **位置**：`D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\core\library_lock.py:83-94`。
- **证据与触发**：两个进程均看到 QLockFile 获取失败，读取同一已死亡 PID；一个进程 `unlink()` 后在重建并 `tryLock()` 前被切换，另一个进程也可删除同一路径并各自成功创建锁。POSIX 允许删除已被其他进程打开的路径，可能形成两个独立锁对象。
- **影响**：两个进程同时进入同一 library，破坏文件/SQLite 一致性。PID reuse 不是问题：复用后的 PID 仍被 `_pid_is_alive()` 视为存活并 fail-closed。
- **建议**：用稳定辅助 OS lock 串行化 stale recovery，或使用 Qt/OS 原子 stale recovery API；不要依赖“检查死亡后直接 unlink”。
- **验证**：Linux/macOS 使用两个独立进程 barrier 竞争已死亡 marker；要求最多一个进程成功。Windows 使用单独的 QLockFile/句柄测试，不套用 POSIX 结论。

### P1-10 token 撤销持久化失败可能跨重启 fail-open，且未纳入完整 session lease

- **置信度**：中高。
- **位置**：`D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\lan\token_revocations.py:48-56,74-99`；middleware `D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\lan\server.py:1533-1559,1602-1633`；DB 方法 `D:\~Vibe-Coding\Projects\AssetsManager_old-bak\AssetsManager\application\auth_service.py:307-323`。
- **证据与触发**：撤销先写内存，数据库写失败只 warning，logout 仍返回 200。冷启动加载时 `_revoked_loaded=True` 在 DB 读取前设置，读取失败后不重试；新实例随后只查空内存。四个 revoke/load/prune 方法没有 `@session_operation`，session close 的 active-operation drain 不会等待它们，可能与数据库关闭并发。
- **影响**：数据库不可读、锁超时、迁移或关闭竞态时，被撤销 token 可能在重启/新实例继续有效，或撤销写丢失。
- **建议**：持久化失败应返回明确失败或进入 durable outbox；加载成功后才设置 loaded，失败时 fail-closed 并退避重试；为 DB-facing 方法纳入 session lease，并将 DB 操作 offload。
- **验证**：注入 `OperationalError`/close race，验证 logout、重启和新 server 是否继续返回 401；测试 session.close 与 revoke 并发。

- WebSocket 有连接数、frame size 和操作超时；其 password/local UI/share token `verify_token` 是 HMAC，不是 PBKDF2。access-key 分支已使用 `asyncio.to_thread()`。
- 分享下载 admission 统一检查 token、过期、path scope 和下载 CAS；订单状态机、delivery quota、购物车 owner/version/checkout 幂等和 receipt 隔离均未发现直接绕过。
- `api.py` 的 `_declared_patterns` 位于 `setup_routes()` 内部，是局部集合；route policy 表按 app 保存，正常多 app/restart 污染不成立。PID reuse 也不是 LibraryLock 漏洞。
- 数据库 migration 的 savepoint、rollback、history 校验、进程 guard 和 retry 结构完整；本轮没有足够证据定性为数据损坏问题。
- 桌面 i18n 三种语言均有 837 keys，新增 viewer key 对齐；WebUI 三字典之间 key 集合相同，但生产调用缺少列出的 7 个 key。
- WebUI 没有生产 `dangerouslySetInnerHTML`/`innerHTML` sink；cookies 不落 localStorage，下载 object URL 有延迟 revoke，主要 external URL 页面已有部分 `http/https` 校验。
