## 1. HIGH（真实数据错误 / DoS / UI 卡死）

### H-G1 Gallery 增量：项目 floor 处新建/移入目录被投影成"截断的 collection"，子树内容整体丢失
- 锚点：`application/gallery_service.py:1341-1345`（`_inside_project` 检查）、`1356-1366`（子遍历）、`1124-1128`（`depth + 1 > child_floor` 的 defensive continue）
- 问题：全量构建在 floor 处走 `_build_project_node` 聚合整棵子树；增量 `_apply_dir_event`（created）只对 `len(parts) > floor` fallback，**floor 处**（`len == floor`）直接 `_build_node` 子遍历——而 `_build_node` 对 `depth + 1 > child_floor` 的子目录直接 `continue`（该分支设计前提是"已在项目内部、已聚合"，增量从 floor 进入时前提不成立）→ 嵌套子目录被跳过且未聚合：纯子目录项目整棵消失（`_build_node` 返回 None），有直接文件则 size/count/artwork 只算直接文件。错误投影还会 `_save_persisted_projection` 落库（重启后 1h TTL 内服务错误数据）。
- 触发：用户移动已填充的项目文件夹到分支下（created 侧）或一次性创建含嵌套内容的目录。
- 修复：created 分支按 floor 分流——`depth == floor` 调 `_build_project_node`；`> floor` 维持 fallback。补测试"floor 处创建/移入含子目录的项目"。

### H-L1 LAN：共享 SQLite 连接被多线程无锁并发使用，违反代码库自身 `db_write_lock` 契约
- 锚点：`core/database.py:955-1013`（契约）· `repositories/storefront_analytics_repository.py:32-101`（worker 无锁 INSERT+commit）· `repositories/order_repository.py:129-230`（多语句事务无锁）· `repositories/tag_repository.py:262-279`（gallery 构建线程无锁读）· `repositories/auth_repository.py:199-207`（`has_active_users`，UI 线程）· `repositories/share_repository.py:243-297`（无锁读）· `lan/server.py:1390-1419`（`_has_active_users`）
- 问题：所有 LAN 服务共享同一连接（`check_same_thread=False`）。绕过锁的 worker `commit()` 会把事件循环线程未提交的事务语句一并提交——订单主表与事件表跨事务分裂，ROLLBACK 无法覆盖已提前提交部分；读写交错还产生间歇 `sqlite3.ProgrammingError`/`database is locked`（与遗留全局写锁 fail-fast 互斥）→ 间歇 500。
- 触发：买家开 storefront（analytics worker 写）+ 管理员同时下单/打标签。
- 修复：全部读写路径统一 `db_write_lock(conn)`；`_has_active_users` 移事件循环线程或专用 worker。

### H-L2 LAN：`/api/info` 公开且跳过限流，在事件循环线程上全库递归遍历 → 无认证 DoS
- 锚点：`lan/routes/system.py:23-87`（`handle_info` 无 await）· `lan/api.py:237`（public + rate_limit="skip"）· `application/project_service.py:546-576`（`_count_projects_recursive`）
- 问题：每次请求对整库递归 `os.scandir`（70k 文件约 0.5-3s），LAN 任意设备无需认证无频率限制连发即冻结事件循环（全部 API + WS 心跳一起停）。landing/storefront 每次刷新也触发。
- 修复：`count_projects` 结果缓存（或 DB 索引计数）；遍历移 `asyncio.to_thread`；至少去掉 rate_limit="skip"。

### H-D1 桌面：会话关闭/切换在主线程**无界等待**不可取消的全局池任务，UI 冻结可达分钟级
- 锚点：`application/context.py:284`（`_finish_close` 的 `wait_for(_active_operations == 0)` 无超时）· `panels/info.py:943-987`（`_SizeTask`）· `panels/_info_parts.py:194-198,251-254`（`_FileInfoTask` 全程持有 operation 租约）· `core/project_data.py:171-189`（`compute_dir_size` 无条目上限）· `panels/file_list/_navigation.py:183-191`（整库 stats walk）
- 问题：`prepare_library_switch` 只清请求注册表不等待/取消已提交 `QThreadPool.globalInstance()` 的任务；worker 持有会话租约到 walk 结束；随后 `close_session → _finish_close` 无界阻塞。大库浏览后立即关窗/切换库 → 冻结数分钟无反馈。
- 修复：① worker 轮询取消令牌（`_async_generation` 失效即退出）；② info 任务专用小池（max 1-2）；③ `_finish_close` 加超时；④ 库统计 walk 支持取消。

### H-D2 桌面：不可取消任务洪泛共享全局线程池，文件扫描被饥饿
- 锚点：`panels/_sidebar_parts.py:49-67`（`_PreloadTask` 无取消）· `panels/sidebar.py:692-714`（搜索防抖每周期新任务）· `panels/file_list/_model.py:232-242`（`_ScanTask` 同池）· `panels/info.py:1411-1423`
- 问题：侧栏搜索每次按键（200ms 防抖）提交全库递归 walk，旧任务不取消只丢结果；与 `_ScanTask` 竞争同一全局池（线程数 = 核数）→ 大库下网格目录扫描延迟、列表长期 loading。
- 修复：`_PreloadTask` 单飞行（新任务置旧任务取消标志，walk 循环内检查）；info 任务专用池；`_ScanTask` 独立高优先级池。

## 5. 总体结论与建议修复顺序

**Gallery 增量状态机与全量构建的语义分歧**是本轮最大风险域（H-G1 静默产出错误数据并落库，M-G1/M-G2 删除后 mtime/封面悬空）——全部集中在最近 3 个 commit 引入的项目聚合语义上，建议优先修复并补增量回归测试。

**LAN 的两个 HIGH**（共享连接无锁并发、/api/info 免限流 DoS）是 70k 库 + 多浏览器 + 长时运行下最可能实际触发的问题，其中 H-L2 是单行级修复（去 skip + to_thread 或缓存）。

**桌面 H1/H2** 是"不可取消任务 + 共享全局池 + 关闭无界等待"的主线，修复需引入取消令牌与专用线程池，改动面较大，建议作为独立批次。

**前端无 HIGH**，M-F1/M-F2 为低成本数据一致性修复。

建议批次：
- **批次 G**（gallery 一致性）：H-G1 + M-G1/M-G2/M-G3 + 回归测试
- **批次 L**（LAN 安全/并发）：H-L1 + H-L2 + M-L1/M-L2/M-L3（性能项 M-L4/M-L5 可选）
- **批次 D**（桌面线程）：H-D1/H-D2 + M-D1/M-D2
- **批次 F**（前端收尾）：M-F1~M-F4 + LOW 各项
