# ZIP 资源预算实施与验收计划

## 本轮目标

在已完成的分块读取、取消传播和临时响应关闭/删除时序之上，限制进程内 ZIP 请求从扫描到下载结束的资源占用。主代理负责方向、接口和最终验收；子代理分别实施预算与清理、扫描与压缩、路由接入。前端开发不在本轮范围内。

## 决策

| 项目 | 默认值或规则 | 理由 |
|---|---|---|
| 在途 ZIP | 4 个/进程 | 覆盖扫描、执行器排队、压缩和响应传输，避免只限制执行线程而让队列无限增长 |
| 单个临时归档预留 | 512 MiB | 与现有 500 MiB 源字节限制匹配，为压缩和归档元数据留出空间；实际写入仍必须检查上限 |
| 全部预留 | 2 GiB/进程 | 四个请求的最大预留之和，多个服务实例和服务重启共用同一预算 |
| 源字节 | 500 MiB/请求 | 保留已有产品限制，并在实际读取时继续检查 |
| 成员数量 | 10,000/请求 | 限制大量零字节文件的中央目录和处理成本 |
| 遍历条目 | 100,000/请求 | 隐藏项、链接等跳过的项也计数，避免绕过扫描成本限制 |
| 目录深度 | 64 层 | 限制目录展开深度，使用流式 scandir 并显式关闭 |
| 资源不足 | HTTP 503，`zip_capacity_exhausted`，`Retry-After: 1` | 在扫描和临时文件创建前拒绝，允许稍后重试 |
| 单请求超限 | HTTP 413，`zip_limits_exceeded` | 错误不带本机路径；估算与压缩共享遍历规则 |

这些是保守的初始容量，不声称已经过设备压测。固定预留会使小归档也占用一个完整名额；本轮优先保证容易验证的总上限，之后再用测量决定是否引入动态预留。

## 所有权不变量

1. 每次准入原子取得一个任务名额与 512 MiB 预留；不足时两个计数均不改变。
2. 每个租约句柄只能释放一次。worker 和响应使用同一预留的独立引用，引用不会重复增加计数。
3. 请求取消不等于 worker 退出；worker 引用一直保留到实际工作结束并完成清理。
4. 成功 ZIP 的初始租约转交给临时响应，只有关闭句柄且删除文件成功（或文件已不存在）才归还。
5. 删除失败时不虚报资源已释放。本轮允许保留预留并拒绝后续工作；后续第五轮已增加当前进程内的清理重试，进程崩溃后的遗留文件回收仍需另行设计。
6. 停止/重启一个 LAN 服务不重置进程预算，因此旧 worker 未退出时不能靠重启获得一套新额度。
7. 普通单文件和分享下载保持现有行为，不占用 ZIP 预算。

## 实施边界

- `zip_resources.py`：线程安全预算、引用租约、进程实例和 AppKey。
- `temporary_file_response.py`：在真正清理成功后一次性回调释放，保留现有 HTTP 行为。
- `zip_sources.py` 与 `_helpers.py`：有界遍历、实际归档输出上限、worker 引用生命周期。
- `downloads.py` 与 `server.py`：生产装配、准入、错误映射和响应移交。

## 验收清单

- 并发准入、精确边界、拒绝不改变计数、重复释放和跨线程引用。
- 隐藏文件、零字节成员、超深目录、链接/junction、遍历提前退出与句柄关闭。
- 实际 ZIP 写入上限覆盖压缩数据、文件名和中央目录，失败后归档不可交付。
- 两类 ZIP 路由满载时不扫描、不创建临时文件；普通下载不受该预算影响。
- 排队取消、执行中取消、完成后配额失败、响应构造失败、慢响应和实际删除之后的释放。
- 多应用及同一服务重启时预算一致；测试实例与生产计数隔离。
- 相关 pytest、完整 LAN/架构/打包配置门禁、Ruff、Pyright；不以 mock 返回成功替代生产装配证据。
