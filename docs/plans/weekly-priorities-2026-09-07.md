# 一周重点工作计划：2026-09-07—2026-09-13

## 1. 本周目标

**将现有多批改动整理为一个能复现、能验收、能回退的候选版本，证明资产数据和核心操作可靠。**

本周以四项成果为目标，其中核心流程证据先覆盖必做项，LAN 测量和包验证受剩余时间及阻断状态约束：

1. 一份与候选源码精确对应的改动清单，以及可以正确运行的 CI/发布预检。
2. 当前版本的测试汇总，包含通过、失败、跳过、未运行及原因。
3. Windows 上启动、切库、备份恢复、WebUI 实时同步和安装包的关键流程证据。
4. LAN 预览/ZIP 的资源基线与下一周取舍结论。

“候选版本”只表示可供验收的本地源码及构建产物；本周计划不自动触发推送、发布或给真实库迁移数据。若关键流程失败，就交付明确阻断项和可复现用例，不以删断言、放宽权限或掩盖跳过来换取通过。

## 2. 优先级与投入边界

按 **一名维护者 + 主代理统筹 + Terra 执行** 规划约 **40 小时周容量**，其中预留 **6–8 小时阻断定位缓冲**。所有候选任务合计约 33–45 小时，超过无缓冲可用额度，因此不承诺全部完成：先保障 W1–W4 与 W7（约 23–31 小时），W5/W6 按剩余容量执行。机器测试等待与工程投入分开记录。周末优先补漏；若按五天工作制执行，周末任务顺延，实际交付前仍必须补完包验收。

| 优先级 | 定义 | 本周内容 |
|---|---|---|
| 必须 | 不完成就无法可靠验收当前改动 | W1 门禁/并行隔离；W2 同版本整合；W3 启动与会话；W4 恢复演练 |
| 条件完成 | 核心工作无阻断且仍有容量时执行；未完成则限制试用/交付结论 | W5 LAN 资源测量；W6 Windows 包验证 |
| 收尾 | 保证后续能继续开发 | W7 总结、残留问题和下周清单 |

这些是工作排序，不是漏洞严重性评级。特别是 ZIP 崩溃后遗留和 Windows 原子打开属于能力缺口/待验证边界，本轮没有证据将它们定为 P0。

时间不足的取舍顺序：先移除全量视觉组合、额外性能优化和 ZIP 持久回收实现；再缩小 W5 数据集及 W6 次要打包模式；始终保留恢复正确性和实际交付模式的冒烟验证。W1/W2 若到周二仍不通过，则后续只做定位和必要验证，不扩大功能范围。

### W1 · 整合基准与测试门禁修正

**为什么先做：** 目前 57 个已跟踪文件改动与多个新增生产模块并存；CI/Release 明确引用不存在的 `setup_cython.py`。B00 隔离了磁盘运行域，但 `worksteal` 无法兑现固定端口测试的分组承诺。

**实施步骤：**

1. 将改动按数据/会话（B01/B02）、失效与前端（B03/B04/B05）、LAN ZIP/预览、启动/搜索性能、测试设施（B00）、文档分组。注明来源、负责人、依赖和已有证据；保护现有用户改动。
2. 捕获包含未跟踪生产文件的验收清单，记录 HEAD、相对路径、SHA-256、依赖版本。不要只复制 HEAD 或只看 `git diff`。
3. 同时修改 `.github/workflows/ci.yml` 与 `release.yml` 的失效 lint 文件清单；顺便逐项核对发布预检的依赖安装、Qt 库与 WebUI dist 准备，发现差异才修。
4. 为 `tests/lan/test_server_lifecycle.py` 确定明确串行方案。推荐短期让需要分组的测试使用 `loadgroup`；如果保留 worksteal，则把真实固定端口用例另作串行阶段。动态端口是后续减少互斥的方向。
5. 用两个 worker 的分组探针记录 PID 和 nodeid，证明同组未分散。不同外层 pytest 进程仍不能共享固定端口；必要时串行运行这些测试进程。
6. 校验 B00 的最新清理异常处理、嵌套 pytest、正常应用子进程继承及退出保存次序；删死代码和改注释限于相关设施，不做全仓库清理。

**涉及文件：** `.github/workflows/{ci,release}.yml`、`pytest.ini`、`tests/conftest.py`、`tests/test_support/`、`tests/lan/test_server_lifecycle.py`。

### W4 · 备份恢复：真实进程中断验证

**为什么重要：** 对资产管理器来说，标签、评分、备注和整理成果的恢复能力比新页面更关键。代码已有入口与恢复意图，历史模拟故障证据仍不能替代实际进程结束。

**测试资产：** 创建专用合成库，含普通/中文/字面百分号路径、嵌套目录、评分 0/5/未评分、标签、备注、收藏和集合。记录数据库与文件清单；先阅读导出 manifest，区分该格式实际承诺保留的元数据与原始资产文件。不要将元数据备份等同于原始资产备份，也不要自动扩大导出格式。

**步骤：**

1. 经当前设置/主窗口入口完成正常导出、校验、恢复、重开库。
2. 先核对恢复阶段并建立测试进程同步机制；当前不能假定生产实现已有暂停挂钩。优先在子进程测试 harness 中包装现有阶段操作，以阶段标记和 IPC 屏障暂停，再由父进程强制结束**该测试子进程**；避免为测试加入默认可触发的生产中断开关。目标覆盖写入恢复意图后、隔离旧数据后、安装新数据的受控边界，不用随机 sleep 猜时机。
3. 新进程启动，观察自动恢复、失败关闭、重试/确认提示；核对恢复后数据属于完整旧状态或完整新状态，不能出现无提示的空库或混合状态。
4. 覆盖一次损坏备份和恢复目录不可写；保留原始库、失败工件和诊断信息。
5. 验证重复重启/恢复幂等，隔离区清理只操作明确归属对象。

**代码入口：** `dialogs/settings_dialog.py`、`window.py`、`app.py`、`application/library_export_service_restore.py`、`application/library_service.py`。

**完成边界：** 进程终止演练不能等同于断电/文件系统持久性验证。6–8 小时内的最低交付是正常恢复、可控终止设施和“隔离旧数据后”一个关键中断点；其余两个中断点能复用设施时补齐，否则逐项标未验收，移入缓冲时段或下周。本周做恢复证据与必要小修；如果需要重写恢复协议，立即登记阻断并单独设计，不强行压缩进一天。

### W5 · LAN 资源测量与容量决策

**启动条件：** W1 已冻结验收版本，W1–W4 没有更高优先级阻断，并且还有可独占机器的测量时段；否则本周仅整理测量方案，W7 如实记录未运行。

**现状：** 在途 ZIP 已有 4 名额、2 GiB 预留等边界；图片单次源字节有 64 MiB 上限。它们不证明并发解码、RSS、批量输出内存和崩溃后磁盘占用安全。

**首轮测量矩阵：**

| 维度 | 最小样本 |
|---|---|
| 业务 | 原图/缩略图、批量预览、目录 ZIP、批量 ZIP、普通单文件下载 |
| 数据 | 普通小图；受控的大尺寸高压缩比光栅图；有代表性的多文件目录；可用时加入 PSD/RAW |
| 并发 | 1、2、4；ZIP 加一次第 5 请求的准入拒绝验证 |
| 网络 | 正常客户端、受控慢读、发送中取消 |
| 策略 | 正常请求与处理期间标签敏感策略收紧 |
| 生命周期 | 请求完成、取消、删除暂时失败及重试后的资源状态 |

**必须采集：** 数据集哈希、机器/内存/磁盘、冷暖缓存、耗时 p50/p95、实际响应字节、峰值 RSS、事件循环延迟、临时盘峰值、在途任务数、取消后回收时间。先小样本渐增；达到机器可承受边界立即停止并保留数据。

**阈值方法：** 先记录单并发基线与空闲噪声，再定义本机预算。建议试验初始预算为单进程 RSS 不超过 `min(2 GiB, 可用内存的 25%)`，事件循环延迟 p95 不超过 100ms，正常关闭/取消后 30s 内名额回到起点；这些只是待评估的验收提案，**不是现行产品承诺或已测结果**。对已注入的 OS 清理失败要核对 pending 状态及重试，不能要求失败期间虚假归还额度。RSS 不必精确返回启动值，但重复批次不能无界增长。

**决策出口：**

- 预算满足：保留当前并发参数，把测量脚本和合理回归阈值归档。
- 解码或输出内存超预算：优先限定在途解码/输出和排队长度，明确拒绝响应、取消与释放合同；再补相关测试，不全面改传输结构。
- ZIP 重启遗留：本周记录真实可复现的遗留占用并完成归属/恢复设计说明。完整持久回收默认排到下周；只有测量证明它已阻止日常使用时才替换低优先任务进入本周。

**后续 ZIP 设计必须回答：** 文件放在哪个专用目录、如何证明归属和判断所有者存活、跨进程互斥、路径被替换/身份不明时怎么办、重启回收如何幂等、磁盘额度和在途预留如何分别核算。禁止按系统 Temp 中相似文件名批量删除。
