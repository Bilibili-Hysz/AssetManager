## 1. 要回答的问题

为什么同一个 onefile 包，在最大化启动、正常退出、重启之后，偶尔无法通过一次 Ctrl+Q 退出？改进探针后通过，是修正了输入缺陷、改变了时序，还是暂时没有遇到原问题？

必须明确故障边界：外部输入生成 → Windows 输入队列/目标线程 → 原生窗口消息 → Qt 键事件 → QAction Shortcut → request_exit → closeEvent → 资源关闭 → 进程结束。不能将“进程没退出”直接归类为关闭死锁。

## 3. 三条可分配定位线

### G1：Windows 输入为什么可能没有到达 Qt？

**优先级：最高。适合熟悉 Windows 输入、ctypes、Qt 原生消息的代理。**

目标：确定输入失败发生在生成、队列投递、消息处理还是 Qt 转换阶段；验证接口与扫描码是否具有因果作用。

负责入口：`scripts/perf/w6_package_functional.py` 的 Win32 绑定、聚焦、逐键发送、GUI 线程诊断；只在本线隔离副本实验。

实施要求：

1. 先读取失败记录，不以新的成功覆盖旧失败。为首次启动和重启分别对齐输入阶段、线程、HWND、单调时钟与事件时间。
2. 冻结同一个 EXE、同一个其余行为一致的驱动；分别比较输入接口与扫描码，不能把两者同时改变后就宣布唯一根因。可用接口 × 扫描码的四组诊断对照；旧输入形式只用于合成库复现，不能回退正式验收驱动。
3. 记录目标线程键盘布局、插入结果及可观测的原生消息；如输入法、完整性级别或输入桌面成为假设，先观测证据，不直接更改用户环境。
4. 发键前后核查前台与真实键盘焦点；区分插入成功、原生消息收到、Qt 收到三种事实。需要系统级跟踪时只针对测试进程和测试时间窗，不采集用户键盘内容。

交付：一张故障层级判定表、最小复现、对照结果及原始事件轨迹。若修复，必须有同条件下修前失败/修后通过证据，并解释为什么修复解决该层问题。仅通过次数增加不足以宣称根治。

### G2：Qt 启动、最大化恢复与退出之间是否存在状态竞态？

**优先级：高。适合熟悉 PySide/Qt 窗口与生命周期的代理。**

目标：独立判断是否存在生产窗口状态问题，解释失败后的最小化来自何处；不要默认 G1 一定能解释全部历史样本。

负责入口：`AssetsManager/app.py`、`AssetsManager/window.py`、`AssetsManager/window_lifecycle_coordinator.py`、`AssetsManager/dialogs/startup.py`、`AssetsManager/widgets/tray.py`。

实施要求：

1. 梳理 StartupWindow 打开库、MainWindow 构造/恢复/显示、StartupWindow 关闭、延迟启动 LAN 的顺序。核对原生焦点与 Qt focusWindow/activeWindow 是否一致。
2. 分清 Qt 最大化/最小化标志、原生 IsZoomed/IsIconic、QWidget 可见性与 HWND 可见性；记录最小化发生时间和能够观测到的触发消息。未知发送者保持未知，不从前台 PID 直接推断责任进程。
3. 分别观察 Shortcut、request_exit、closeEvent、shutdown_resources、lastWindowClosed、aboutToQuit。只有确认调用已进入且不返回，才分析关闭阻塞；必要时捕获该进程线程栈。
4. 避免一上来加全局快捷键、无条件 app.quit、延长超时或固定等待。若能证明生产竞态，给出最小修复与恢复/重开语义的回归证据。

交付：窗口状态时序图、可重现的触发条件、相关调用栈/消息与最小测试。未发现生产缺陷也是合法结论，但须说明观测范围，不能用“代码看起来正常”替代实验证据。

### G3：观察器是否改变了故障概率？

**优先级：高。适合擅长实验设计、性能追踪和独立复核的代理。**

目标：检查现有诊断是否改变导入时机、PySide 回调绑定或事件处理时序，并对 G1/G2 的结论作因果审查。

负责入口：归档观察器、诊断 harness 和结果汇总；不拥有生产文件，不与 G1 同时修改正式 W6 驱动。

实施要求：

1. 比较早期提前导入/方法包装观察器、保留方法对象的 sys.monitoring 观察器，以及加入原生消息过滤器后的差异；不能把这些不同条件合并成一个成功率。
2. 固定输入驱动与候选包，对照无观察器、内存缓冲记录、同步写文件记录。记录缓冲丢失/溢出，并在正常退出和失败超时都保存已有事件，避免只拿到成功日志。
3. 在运行前写明样本数、顺序、失败后的处理和总时间上限；保留每次结果，不做“重试直到通过”。报告给出各组失败数/总数与条件，不用小样本宣称零故障。
4. 检查 API、扫描码、聚焦策略、额外查询和日志成本是否同时改变。若多个因素同时变化，将结论降为关联证据，再提出最小下一步实验。

交付：实验条件清单、完整样本索引、观察干扰评估，以及对 G1/G2 根因结论的独立接受/拒绝理由。没有复现时必须写“本实验未复现”，不能写“问题不存在”。

## 5. 主案结案标准

根因定位完成应同时具备：

1. 至少一个失败样本能明确落在某个链路边界，说明此前哪些解释成立、哪些证据仍缺失。
2. 最小触发条件或可解释的时序窗口，以及一次能够区分竞争假设的对照实验。
3. 如果提交修复，说明修正的是测试驱动、环境约束还是生产代码；验证修前/修后行为，并保留 30 秒正常退出、元数据和窗口状态持久化断言。
4. 最终使用不含诊断插件的正式驱动验收；受影响合同测试通过，版本与证据对应。

若定位到的是外部输入限制，可用可验证的驱动修正或明确环境约束结案，不要求为了交付而制造生产补丁。时间预算耗尽但根因不明时，交付“未定位”报告、已排查边界和下一项区分实验，不包装为根治。
