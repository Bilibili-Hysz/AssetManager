## 2. G3 准备门槛

| 缺口 | 本次需要达到的标准 |
|---|---|
| 相位混用 | 独立 run_id、launch_phase、call_phase；GUI/父进程 PID 与创建身份对应；旧数据只做派生映射，不改原日志 |

## 3. 固定负载与受控干预

保留归档 f989 驱动的完整 info、登录、字体、单/批缩略图、元数据、live change、窗口持久化、重启负载。保留候选 AssetManager.exe 文件名及其哈希；不换输入接口、扫描码、超时阈值、Q 次数。

三种条件，各两个周期；每周期首退为未干预参考，重启退为预登记目标相：

| 条件 | 唯一干预 | 说明 |
|---|---|---|
| C | 自建辅助进程存在，但不激活/不最小化目标 | 控制辅助程序本身的负载 |
| F | 辅助窗口请求并实际取得前台，目标不主动最小化 | 若 OS 拒绝或未观测到前台切换，记注入无效 |
| M | 控制器只对已验证身份的合成目标请求最小化，不主动激活辅助窗口 | 操作必须实测生效；窗口管理引发的后续前台变化作为结果记录 |

固定顺序 C→F→M→M→F→C。全部条件保留相同辅助进程、观察器模式及同步屏障；观察器模式在预登记中选定，不再叠加 O0/O1/O2 因子。

干预点先选“重启相 Ctrl-down 后、Q 前安全检查之前”，以驱动握手定位，不靠随机 sleep。这样先验证输入保护边界；若该点均被驱动安全拒绝/恢复，它只说明保护按合同工作，**不构成历史 Q 已发送后超时的复现**。没有剩余预算和可区分假设时就此收口，不拆掉保护强求失败。

未来若确需研究 Q 已发送后的竞争，另登记“Q-down 调用完成”的单一屏障与接收顺序判据，不混入本矩阵，不把动作完成当 Qt 已接收。

只操作本批次创建的目标和辅助窗口，不最小化整个桌面，不关闭 QQ 等用户应用，不向未知前台发键。每次操作校验 PID 创建身份及 HWND 所有者；丢失目标即停止本次动作。只释放本轮持有的按键，记录异常清理，不以清理成功记 PASS。

## 4. 结果分类与停止条件

| 状态 | 判据 | 是否证明历史故障 |
|---|---|---|
| PASS | 注入合同满足（C 为未干预）、驱动正常完成、两次退出及持久化通过 | 否 |
| EXPECTED_REJECTION | 干预造成不安全输入状态，驱动在 Q 前明确拒绝；退出未完成 | 否；保护行为成功，但不能计入正常退出数 |
| RECOVERED | 驱动按既有聚焦流程恢复并正常完成，轨迹可核对 | 否；另列于摘要，退出数按实际统计 |
| INVALID | 注入未生效、身份/基线不符、记录器或控制器失败 | 否 |
| FAIL | 未预期的真实目标行为，含已安全发送后 30s 未退出 | 候选样本；需按层判读后确定与历史是否同型 |
| NOT_RUN | 停止条件或预算导致未执行 | 无结论 |

最多 6 周期，计划上限 12 次正常退出机会，实际完成数不能把 EXPECTED_REJECTION 算进去。首个 FAIL 立即保全日志、窗口状态及父子进程状态，并停止整批；主代理决定后续一个区分实验是否值得另立预算。遇记录器异常停止修工具，不在同一批次静默升级版本。90 分钟或 G 总人时到限均停止。

## 5. G2 退出等待预算评估

初始可达反例：LibraryService.close → _run_owned_teardown → DatabaseManager.close_library → _write_gate.write → 无 timeout 的 Condition.wait_for。Service 自身的 _closing/_closing_roots/_restore_reservations 也是候选等待条件。Runtime 条件锁、listener、数据库连接锁、LAN 的累计等待继续沿实际路径核对。

每个等待点填写：

| 字段 | 要求 |
|---|---|
| 调用条件与线程 | 谁进入、GUI 是否同步等待；锁获取本身也登记 |
| 被等待的所有者 | 哪个 worker/session/reservation/reader，何处释放并 notify |
| 当前时间上界 | 单点 timeout、重试与累计预算；未知写未知 |
| 失败后状态 | open/closing/pending/failed/closed 的转换；哪些对象仍不得释放 |
| 最小复现 | 合成 barrier 控制的竞争；用事件握手，不靠碰运气 sleep |
| 修复取舍 | 统一 deadline、异步协调或重试合同的成本；不是简单加一个数字 |

若建议补丁，必须证明：超时不提前关闭仍被使用的 DB、不释放活跃 root lock、不伪装 drained、不破坏重试及重开；GUI 的响应策略与进程退出策略明确。测试必须能区分有进展的慢清理与真正卡住的所有者。

本周默认交付评估，未捕获生产失败不阻止讨论防御设计，但不能称已修复历史根因。实现需主代理根据 P1 任务与剩余预算单独纳入范围。
