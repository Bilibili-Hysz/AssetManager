## 环境坑（重要，下次直接复用）

1. **必须用系统 Python 3.14**，WorkBuddy 托管的 3.13.12 是干净环境，没装 pytest/PySide6/aiohttp：
   `C:/Users/86177/AppData/Local/Programs/Python/Python314/python.exe`

2. **pytest 必须带 `--basetemp`**，否则必崩：
   ```
   PermissionError: [WinError 5] 拒绝访问。'C:\Users\86177\AppData\Local\Temp\pytest-of-86177'
   ```
   系统 temp 被特权进程锁死（`ls` 该目录也 Permission denied），`pytest.ini` 的 `-n auto`（xdist）
   在 sessionstart 建 basetemp 时炸。绕行：`--basetemp=.pytest-xxx`
   —— 注意 `.gitignore` 注释显示开发者早知此事，但 basetemp 从未写进 `pytest.ini`

3. **串行跑测试要覆盖 addopts**：`--override-ini="addopts=-ra"`
   （直接用 `-p no:xdist` 会导致 ini 里的 `-n auto` 无法解析而报 unrecognized arguments）

4. **`gh` 装了但连不上 GitHub**：`api.github.com` 返回 EOF，查不了云端 CI 运行历史

## 关键发现

### 好得出乎意料（别当成烂项目）
- 10 个 CI 门禁脚本本地实测**全绿**（含 AST 12 层依赖 DAG）——分层是真守住的
- ruff 全绿；**0 个 TODO/FIXME**；注释死代码仅 12 处（95,898 行里）
- **30/30 conventional commit**；`.git` 仅 11MB；硬编码凭据 0 命中
- 4,259 个测试用例；283→290 测试文件

### 真问题
1. **30 个 commit 从未推送**（`origin/master...HEAD` = 0/30），只在本机。README 说"无 remote"已过期——remote 有，代码没推
2. **`tests/unit/test_bootstrap.py` 让 pytest 进程硬崩溃**（无 traceback、exit 1），51 个用例全废；跑 unit 全量时崩在 9% 处。崩溃点在 autouse fixture `_cleanup_stores`（`tests/conftest.py:514`）的 `QThreadPool.globalInstance().waitForDone()` 与 `ThreadSafeSingleton.get(DatabaseManager).close()`
3. **RuntimeData 393MB**：303 个测试残留 `library_*` 与真实资产库 `Avatars（角色）_d5cd47e2cd`(12MB) 混住。根因是设计死结——`clean_runtime.py:16` 明确"刻意保留 RuntimeData"；`conftest.py:550` 的 `except Exception: pass` 静默吞清理失败
4. 本地质量门（README 5 条）≠ CI 门禁（10 脚本），且**无 pre-commit**
5. 文档自审结论过期 2 条（"无 remote"、"release 无测试前置"），且是用旧坏消息掩盖新坏消息
6. 僵尸配置：`.gitignore` 为 `previewer-dist` 留了带解释的规则，但代码零引用、目录不存在。**3D 预览功能确实不存在**（.glb/.gltf/.fbx/.obj 仅在 asset_filters/format_utils 做格式识别）
7. `check_audit_reports.py` 空转：`no audit manifest registered`

### 我自己犯的错（记录以自省）
- 首轮全量测试我设了 `timeout 900`（15 分钟），导致测试被自己 kill，一度误判为"测试 38 分钟跑不完"。
  **结论已修正**：不是项目慢，是我的墙。下次跑长测试别设短 timeout
- 一度把两处 `time.sleep(30)` 当成测试慢的元凶，读上下文后确认**都是良性的**
  （子进程持锁/挂起，父进程 `terminate()` + `wait(timeout=5)`，不会真等 30 秒）

## 核心判断（可复用的洞察）

> **长线 Vibe Coding 的隐蔽规律：一次性就能生成的产物（脚本/文档/ADR/配置）严重过剩，
> 需要持续执行的动作（推送/清理/复核/删除）严重不足。**

这个项目是教科书样本：13 个门禁脚本、402 篇文档、详尽自审表——都造出来了且质量很高；
但代码没推送、垃圾没清理、文档在过期、废弃配置没删。
每一件单看都对，合起来是一条没人走的断链。

**修复方向不是重构代码，是补执行闭环。**
